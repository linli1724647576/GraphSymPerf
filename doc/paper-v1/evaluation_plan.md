## 3 执行阶段

1. **环境门禁：** 离线测试、故障注入和严格 doctor；记录 CPU、系统、数据库、驱动、镜像、生成器与仓库哈希。
2. **递进试验：** 每个数据库依次完成 1×10、1×100、1×1,000。任何证据链、资源预算或恢复失败均阻止正式长跑。
3. **正式运行：** 固定 7×16×1,000 矩阵。完整和不完整分片分开报告，不补写缺失接受对。
4. **候选验证：** 发现样本不能在验证中复用；每个候选使用两个新进程和相同图快照。
5. **归约与再验证：** 原始验证通过后才归约；归约结果重新执行完整验证。
6. **去重与提交：** 按触发结构、症状、版本、平台和修复范围查重。提交后冻结观察窗口并保存状态证据。

## 4 基线

### 4.1 外部基线

**GRev** 是必须比较的最强直接基线。比较条件应固定共同支持的数据库、Cypher 子集、硬件和时间/接受预算，至少报告：生成成功查询数、候选数、可稳定复现数、人工归约时间和开发者可提交数。

若 GRev artifact 无法支持某个当前目标，不应把零产出当作 GraphSymPerf 优势。应把该单元格标记为 `not comparable`，同时在可兼容目标上完成比较。

**GraphQE** 不是性能检测基线，而是规则证书的外部证明工具。对于其支持的 Cypher 子集，应统计核心变换实例的证明成功、超时和不支持比例，并比较证明成本与动态接受门禁成本。GraphQE 无法覆盖的结构必须保留为明确边界，不能据此宣称证书已经得到通用证明。

### 4.2 内部基线与消融

| 变体 | 回答的问题 | 安全限制 |
|---|---|---|
| screen-only | 独立验证过滤了多少发现阶段候选？ | 禁止提交该变体产出 |
| one-session validation | 第二会话减少多少不稳定候选？ | 仅离线分析 |
| no A/A-B/B control | 噪声门槛对候选数量的影响？ | 只比较判定差异 |
| dynamic-equivalence-only | 安全证书减少多少不适用/偶然相等变换？ | 语义风险产出不得提交 |
| no reducer | 归约对查询规模、复现和开发者反馈的影响？ | 候选仍需原始验证 |
| per-rule family | BOOL 与 SYM 规则的覆盖和产出是否不同？ | 接受预算按规则报告 |

## 5 分析方法

- 所有比率同时报告分子和分母；不只展示成功案例。
- 运行时以配对样本为单位，保留 AB/BA 顺序；报告中位数、置信区间和绝对时间差。
- 按数据库、规则、分片和候选阶段分层，避免把跨版本累计 issue 混入正式分子。
- 对 2×/3× 倍率、CI 下界、A/A 分位数和图规模做敏感性分析。
- waiting reply 视为未决样本，不用于估计开发者确认率；观察窗口外仍未回复者单列。
- 性能异常的根因表述为假设，除非维护者回复、修复提交或受控实验直接支持。

## 7 完成判据

- 112 个分片终态均可审计；`INCOMPLETE` 不伪装成 completed。
- 所有 RQ 的分母、拒绝原因和版本信息完整。
- GRev 至少在一个共同目标上完成公平比较，或给出可复核的不可比较原因。
- GraphQE 对核心规则实例的覆盖与局限已有实测结果。
- 所有验证通过候选均有原始与归约后验证；部分归约不进入提交产出。
- 正文中的 `[RESULT GAP]` 全部由实际产物替换，不使用预测值。
