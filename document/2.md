如果上一轮任务正确完成，你的项目预期会从“能发现性能异常的原型工具”升级到一个更适合做论文实验的平台。它仍然不会自动替你证明所有候选都是 bug，但它会具备三个关键能力：能衡量等价变换探索了哪些优化器行为，能根据历史反馈优先探索更有效的变换规则，能把大量原始候选压缩成可人工复核的 unique issue candidates。

也就是说，下一步服务器全量实验的目标不应该是“跑出很多 case”，而是：

```text
生成大量语义等价查询对 / 查询族
  -> 验证结果等价
  -> 提取 plan/profile/runtime 差异
  -> 计算 Plan Metamorphic Coverage
  -> 反馈调整 bool_redundancy / symmetry 规则选择
  -> 聚类去重，得到 unique performance anomaly candidates
  -> 对代表性候选做 runtime/reducer/replay
  -> 人工筛选并提交开发者 issue
```

你真正用于论文的不是 raw candidates 数量，而是经过分层过滤之后的：

```text
profile-supported candidates
runtime-supported candidates
unique issue candidates
reported issues
developer-confirmed / fixed / wont-fix / upstream cases
root-cause taxonomy
PMC coverage growth
feedback-guided strategy improvement
```

# 1. 执行完上一轮任务后的预期效果

上一轮任务完成后，项目应该至少具备这些研究能力。

第一，**每个等价查询对都会产生 PMC evidence**。也就是说，不只是候选才有记录，所有结果等价的 case 都会被转化成计划级覆盖信息，例如：

```text
operator_delta: Filter added
access_delta: NodeByLabelScan -> AllNodeScan
predicate_delta: predicate residue introduced
barrier_delta: Sort / Distinct / Aggregation added
work_delta: db_hits 10x bucket
cardinality_delta: estimated rows 100x bucket
```

这样你可以回答论文里的问题：bool_redundancy 和 symmetry 到底探索了优化器的哪些行为，而不是只说“我跑了很多查询”。

第二，**feedback scheduler 会开始根据历史结果选择规则**。例如某些 bool rule 经常产生 result-equivalent 且 profile-supported 的 case，并贡献新的 PMC units，那么它的权重会上升；某些 symmetry rule 经常 skip、无效、重复 plan，则权重下降。这样服务器长时间运行时，不会一直平均浪费资源。

第三，**候选会被分类和去重**。以前可能 100 个 candidates 其实都是同一个根因，现在应该能归并成若干 issue families 和 unique issues，例如：

```text
Raw candidates: 1240
Profile-supported candidates: 310
Runtime-supported candidates: 48
Issue families: 21
Unique issue candidates: 37
Top representatives: 20
```

这会极大降低你人工复核和提交 issue 的成本。

第四，**实验 artifact 会更像论文证据**。每次 run 应该输出：

```text
pmc_summary.json / md
pmc_evidence.jsonl
feedback_summary.json
rule_stats.json
candidate_signatures.jsonl
clustered_summary.json / md
issue_families.json
unique_issues.json
duplicate_groups.json
```

这些文件能直接支撑论文表格：变换规则贡献、覆盖度增长、候选分布、根因分布、去重前后数量变化。

第五，**你的工具会具备“寻找未发现 issue”的基础能力**。但还差一个很重要的层：全量实验调度、服务器分片执行、断点续跑、实验矩阵管理和结果聚合。上一轮任务主要补的是研究方法层；为了服务器实验稳定运行，建议再补一个 experiment runner / experiment preset 层。

# 2. 现在还需要补齐的“实验预备能力”

如果你的目标是本地写好代码，上传服务器后直接跑全量实验，那么我建议继续让 Codex 增加一个轻量的实验管理层。它不改变研究主线，只负责把不同评估实验配置化、可复现化、可分片执行。

建议新增能力：

```text
1. experiment manifest：用 YAML 描述完整实验矩阵。
2. shard execution：同一个实验可以拆成多个 shard 并行跑。
3. resume：服务器中断后能继续跑，不重复已完成 case。
4. doctor/preflight：检查数据库连接、PROFILE 支持、环境变量、Docker 版本、磁盘空间。
5. aggregate：把多个 shard 的结果合并成一个总 summary。
6. triage queue：从 clustered unique issues 中挑选 top representatives。
7. validation stage：对 top representatives 做 runtime repeat / reducer / replay。
8. report export：自动生成论文表格所需 JSON/CSV/Markdown。
```

这不是工程洁癖，而是全量实验必须要有的能力。否则你在服务器上跑 2 天后断掉，或者多个系统输出结构不一致，后面会很痛苦。

# 3. 全量实验应该分成哪些阶段

我建议你的实验不要一上来就直接全系统全量跑。应该分成六个阶段。

## 阶段 A：Known Issue Replay Sanity Check

目的不是发现新 bug，而是验证工具、adapter、profile parser、PMC extractor、clustering 都能正常工作。

输入是你已有的 issue case：

```text
neo4j_13783_fixed
neo4j_13814_wontfix
memgraph_4208_pending
falkordb_2081_pending
arcadedb_4405_fixed
apache_age_2428_upstream
```

预期输出：

```text
结果等价是否仍成立
profile/plan symptom 是否仍可复现
PMC units 是否能正确提取
candidate signature 是否稳定
developer_status 是否正确读取
```

这一步必须在服务器主实验前跑。它相当于实验环境的端到端冒烟测试。

建议命令形式：

```bash
graph-sym-perf replay --all-known --config config/experiments/replay_known.yaml
```

---

## 阶段 B：小规模 Calibration Run

目的：校准各系统的阈值、timeout、profile 解析可靠性和 runtime 噪声。

每个系统先跑 100 到 500 个 seed case，不追求发现 bug。

建议配置：

```text
systems: 每个目标系统都跑
source: gdsmith + ldbc/templates
transform_families: bool_redundancy + symmetry
feedback: disabled
coverage: enabled
runtime_validation: disabled 或 very light
max_cases_per_system: 100~500
```

你需要观察：

```text
有效查询率
结果等价率
非空率
PROFILE 可用率
平均单 case 时间
timeout 比例
PMC new unit 增长曲线
raw candidate 比例
明显误报模式
```

这一步会决定主实验阈值。例如，如果某系统 PROFILE rows 本来就很噪，不能用 rows 作为强信号；如果某系统 DB hits 不可用，就不要把 DB hits 作为 hard requirement。

---

## 阶段 C：Main Effectiveness Run

这是寻找“previously unknown performance anomaly issues”的主实验。

主实验建议只使用你的两个核心等价变换族：

```text
bool_redundancy
symmetry
```

开启：

```text
coverage.enabled = true
feedback.enabled = true
clustering.enabled = true
runtime_validation.mode = selective
reducer.enabled = selective
```

重点是大量生成、自动去重、自动选代表。

建议主实验矩阵：

```text
每个系统：
  mode = both_feedback
  transform_families = [bool_redundancy, symmetry]
  safety_tier = strict + conservative
  exploratory = false 或单独跑
  max_cases = 10,000 ~ 100,000
  shards = 4 ~ 32，根据服务器资源
```

如果服务器资源充足，每个系统至少 20k 到 50k seed case 才比较像全量实验。对于初稿，可以先 10k 起步。

主实验输出的核心数据应该是：

```text
total seeds
generated query pairs / families
valid cases
equivalent cases
non-empty cases
profile-supported candidates
runtime-supported candidates
raw candidates
issue families
unique issue candidates
top representatives
reported issues
developer-confirmed / fixed 数量
PMC total units
PMC new units
PMC by family / rule
feedback top rules
```

---

## 阶段 D：Ablation Run

主实验跑完后，为了论文有效性评估，需要做消融实验。否则评审会问：到底是 bool_redundancy 有用，还是 symmetry 有用？feedback 是否真的有用？PMC 是否只是报告指标？

建议最小消融矩阵：

```text
1. bool_only_static
2. symmetry_only_static
3. both_static
4. both_feedback
```

如果资源够，再加：

```text
5. bool_only_feedback
6. symmetry_only_feedback
7. both_feedback_without_pmc_reward
8. both_feedback_with_pmc_reward
```

每组不一定跑和主实验同样规模，可以用 20% 到 30% 的预算。例如主实验每系统 50k，消融每系统 10k。

论文里可以比较：

```text
每 1000 cases 的 PMC new units
每 1000 cases 的 profile-supported candidates
每 1000 cases 的 unique issue candidates
等价率
timeout 率
重复率
```

你需要证明 feedback-guided 的价值不是“跑得更多”，而是“同样预算下探索更多不同计划差异，产生更多高质量 unique candidates”。

---

## 阶段 E：Oracle Reliability Run

这一阶段用于支撑“为什么不用 runtime-only”。

对主实验中的候选做分层验证：

```text
plan-only candidates
profile-supported candidates
runtime-supported candidates
developer-reported candidates
```

建议抽样策略：

```text
从每个系统、每个 transform family、每个 root-cause label 中抽 top representative
每个 representative 做 repeated runtime validation
```

例如：

```text
warmup = 3
repeats = 9 或 15
median ratio threshold = 2.0
absolute delta threshold = 20ms 或 50ms
IQR stability threshold = 0.5
```

输出：

```text
plan-only 中有多少 runtime 不稳定
profile-supported 中有多少 runtime 稳定变慢
runtime-only 是否产生大量噪声
combined oracle 的 precision 是否更高
```

这一阶段不需要覆盖所有 raw candidates，只需要覆盖聚类后的 representatives。

---

## 阶段 F：Triage and Issue Reporting Run

这是从实验数据走向真实 issue 的阶段。

流程：

```text
clustered unique issues
  -> 按优先级排序
  -> 选 top N representatives
  -> reducer
  -> runtime validation
  -> manual check result equivalence
  -> search existing issue tracker
  -> generate issue draft
  -> submit issue
  -> record developer_status
```

优先级建议：

```text
1. profile-supported 且 runtime-supported
2. db_hits / actual_rows ratio 高
3. PMC units 显示清晰根因，例如 PredicatePushdownBlocked / AccessPathRegression
4. reducer 后查询短
5. graph reproducer 小
6. 同类系统中多个 DBMS 复现
7. 不是 exploratory rule
```

对“previously unknown”的判断，需要你在提交前人工搜索对应系统 issue tracker，避免重复报告。工具可以辅助生成搜索关键词，但最终最好人工确认。

# 6. 服务器上执行实验的推荐流程

上传代码前，本地只需要做这些：

```bash
python -m pytest
graph-sym-perf --help
graph-sym-perf doctor --config config/experiments/calibration.yaml
graph-sym-perf replay --all-known --dry-run
```

服务器上建议按这个顺序执行：

```bash
# 1. 检查环境
graph-sym-perf doctor --config config/experiments/main_effectiveness.yaml

# 2. 回放已知 issue，确认 adapter/profile/parser 正常
graph-sym-perf replay --all-known --config config/experiments/replay_known.yaml

# 3. 小规模校准
graph-sym-perf experiment run --manifest config/experiments/calibration.yaml

# 4. 查看校准报告，必要时调 timeout/threshold
graph-sym-perf experiment aggregate --run-root runs/calibration

# 5. 主实验，分片执行
graph-sym-perf experiment run --manifest config/experiments/main_effectiveness.yaml --shard 0 --num-shards 16
graph-sym-perf experiment run --manifest config/experiments/main_effectiveness.yaml --shard 1 --num-shards 16
...
graph-sym-perf experiment run --manifest config/experiments/main_effectiveness.yaml --shard 15 --num-shards 16

# 6. 聚合所有 shard
graph-sym-perf experiment aggregate --run-root runs/main_effectiveness_2026_01

# 7. 生成 triage 队列
graph-sym-perf triage --run-dir runs/main_effectiveness_2026_01 --top 100

# 8. 对 top unique issues 做 runtime/reducer/replay
graph-sym-perf validate --triage runs/main_effectiveness_2026_01/triage_top100.json

# 9. 生成论文表格和 issue drafts
graph-sym-perf report --run-dir runs/main_effectiveness_2026_01
```

如果这些命令当前还没有，就应该让 Codex 补齐。否则你上服务器后只能手动拼脚本，后续结果很难复现。

# 7. 找 previously unknown issue 的实际筛选策略

全量实验结束后，你不要直接从 raw candidates 里挑。应该从 `unique_issues.json` 或 `triage_top.json` 中挑。

优先挑这些：

```text
1. support_level = profile_supported 或 profile_and_latency_supported
2. root_cause 是明确的：
   - BooleanSimplificationMissing
   - PredicatePushdownBlocked
   - AccessPathRegression
   - PatternOrderSensitivity
   - AccessPointInstability
   - BarrierInsertion
   - WorkInflation
3. metric ratio 大：
   - db_hits >= 5x
   - actual_rows >= 5x
   - latency >= 2x
4. reducer 后查询足够短
5. reproducer graph 足够小
6. 不依赖 exploratory rule
7. 不是 estimated-only，或者 estimated-only 也有明确 plan-shape 变化
```

低优先级：

```text
1. 只有 estimated rows 变化，没有 actual/profile/runtime 支持
2. 只有 runtime 变化，但 profile/plan 无明显变化
3. 查询极长，reducer 无法缩小
4. 变换规则太怪，解释成本高
5. 同一 root cause 已经有更小代表
```

提交 issue 前，每个候选都应该经过：

```text
result equivalence replay
profile replay
runtime replay
minimal reproducer
existing issue search
issue draft review
```

这样你报告出去的 issue 更可能被接受。

@dataclass(frozen=True)
class ExperimentManifest:

============================================================

实现：

graph-sym-perf doctor --config config/experiments/main_effectiveness.yaml

检查：
1. 配置文件可解析。
2. 输出目录可写。

输出：
- preflight.json
- preflight.md

四、Shard / Resume
============================================================

实现分片执行：

graph-sym-perf experiment run \
  --manifest config/experiments/main_effectiveness.yaml \
  --shard 0 \
  --num-shards 16

要求：
1. 每个 shard 的 run_dir 独立，例如 runs/main/shard_000。
2. 每个 case_id 稳定，包含 experiment_id、system、shard、local_index、seed。
3. 如果 resume=true，已完成 case 不重复跑。
4. 每 N 个 cases 写 checkpoint.json。
5. 中断后重新运行同一 shard 能继续。
6. 每个 shard 输出自己的 summary.json、pmc_summary.json、feedback_summary.json、clustered_summary.json。

实现 checkpoint：
- completed_case_ids
- failed_case_ids
- skipped_case_ids
- last_seed_index
- feedback_state snapshot
- pmc_state snapshot
- random state / deterministic seed info

不需要复杂数据库，只用 JSON 即可。

7. ratio 类指标保存分布，不要简单平均；至少输出 count、median、p90、max。
8. 每个 system 单独统计，也输出 overall。

六、Triage
============================================================

实现：

graph-sym-perf triage \
  --run-dir runs/main_effectiveness_2026_01 \
  --top 100

从 aggregate_unique_issues.json 选择 top representatives。

排序策略：
1. developer_status fixed/confirmed/reported 优先，如果有。
2. support_level: profile_and_latency > profile_supported > latency_supported > plan_only。
3. root_cause 清晰优先，例如 PredicatePushdownBlocked / AccessPathRegression / WorkInflation。
4. db_hits / actual_rows / latency ratio 高者优先。
5. pmc_new_units 多者优先。
6. reducer 后 query 短者优先，如果已有 reducer 信息。
7. strict/conservative 优先于 exploratory。
8. case_id 稳定排序。

输出：
- triage_top100.json
- triage_top100.md
- triage_top100.csv

每个条目包含：
- rank
- case_id
- system
- transform_family
- transform_rule
- root_cause_labels
- support_level
- metric summary
- pmc summary
- artifact paths
- issue draft path if exists

七、Validation Stage
============================================================

实现：

graph-sym-perf validate \
  --triage runs/main/triage_top100.json \
  --runtime-repeats 15 \
  --reduce

作用：
1. 重新加载 representative case。
2. 重放 base/transformed query。
3. 再次验证 result equivalence。
4. 重跑 profile。
5. 可选 repeated runtime validation。
6. 可选 reducer。
7. 更新 validation_summary.json。
8. 为通过验证的候选生成 issue_draft.md。

如果 reducer 还只是 skeleton，可以先支持：
- no-op reducer
- query length / graph size 记录
- validation replay

# 10. 你现在的行动顺序

我建议你按这个顺序推进：

```text
1. 先让 Codex 完成 PMC / feedback / clustering。
2. 本地跑完整 pytest。
3. 再让 Codex 增加 experiment runner / manifest / shard / resume / aggregate / triage。
4. 本地用 fake 或 small calibration 配置跑通。
5. 上传服务器。
6. 先跑 replay_known。
7. 跑 calibration。
8. 调阈值和 timeout。
9. 跑 main_effectiveness。
10. aggregate + triage。
11. 对 top candidates 做 validation/reduction。
12. 人工筛选并提交新的 issue。
```

最关键的是不要把“主实验”和“工具调试”混在一起。服务器主实验开始前，代码必须已经能稳定输出 PMC、feedback、clustering、aggregate、triage；否则全量跑出来的数据会很难整理，也很难写进论文。
