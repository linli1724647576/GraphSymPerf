# Missed optimization: a decisive AND guard is applied after an expensive graph subquery

Hi Neo4j team,

I found that an inexpensive node predicate is applied after a correlated `EXISTS` subquery, even when that predicate already makes the conjunction false. An equivalent `CASE` expression over the same graph avoids the unnecessary expansion and returns exactly the same result.

I reproduced this on Neo4j 2026.09.0 Community, Cypher 25, in Docker on macOS ARM64.

### Reproduction

Please use an empty database and create this graph:

```cypher
CREATE INDEX gsp_cost_lookup IF NOT EXISTS
FOR (n:GspAnchor) ON (n.uid);

CREATE (:GspAnchor {uid: 1, keep: false});
CREATE (:GspAnchor {uid: 2, keep: true})
       -[:GSP_EXPAND]->(:GspLeaf {uid: 3, mark: true});

MATCH (u:GspAnchor {uid: 1})
UNWIND range(1, 400000) AS i
CREATE (u)-[:GSP_EXPAND]->
       (:GspLeaf {uid: 895440 + i, mark: false});

CALL db.awaitIndexes(60);
CALL db.prepareForReplanning();
```

Anchor 1 has `keep=false` and a large branch with no matching leaf. Anchor 2 has `keep=true` and one matching leaf. No auxiliary reference relationships are needed.

Run the guarded conjunction:

```cypher
PROFILE
MATCH (u:GspAnchor)
WHERE (
  ((coalesce(u.keep, false) = true AND u.uid = u.uid)
    OR NOT (u.uid = u.uid))
  AND EXISTS {
    MATCH (u)-[:GSP_EXPAND]->(leaf:GspLeaf)
    WHERE (leaf.mark = true AND u.uid = u.uid)
       OR NOT (u.uid = u.uid)
  }
)
RETURN u.uid;
```

Compare it with the same condition written using `CASE`:

```cypher
PROFILE
MATCH (u:GspAnchor)
WHERE CASE
  WHEN (
    (coalesce(u.keep, false) = true AND u.uid = u.uid)
      OR NOT (u.uid = u.uid)
  ) = false THEN false
  ELSE (
    ((coalesce(u.keep, false) = true AND u.uid = u.uid)
      OR NOT (u.uid = u.uid))
    AND EXISTS {
      MATCH (u)-[:GSP_EXPAND]->(leaf:GspLeaf)
      WHERE (leaf.mark = true AND u.uid = u.uid)
         OR NOT (u.uid = u.uid)
    }
  )
END
RETURN u.uid;
```

### Observed behavior

Both return the single row `u.uid = 2`. The `CASE` form is `CASE WHEN L=false THEN false ELSE L AND H END`, so it preserves the conjunction's TRUE/FALSE/NULL behavior without changing any edges.

These are the relevant recorded PROFILE fields, shown as a compact excerpt:

```text
Conjunction:
Operator        Rows     DB Hits   Relevant detail
Filter             1           1   keep condition
SemiApply          1           0
  Expand(All) 400001      400004   (u)-[:GSP_EXPAND]->(leaf)
  Filter           0      400002   leaf.mark condition
Total DB Hits: 800013

CASE:
Operator           Rows   DB Hits   Relevant detail
Filter                1        17   CASE condition with EXISTS
NodeByLabelScan       2         3   u:GspAnchor
Total DB Hits: 20
```

The original plan evaluates `SemiApply` before the outer `keep` filter, so it visits the entire branch of anchor 1. The CASE plan avoids that branch. The conjunction was about 86 times slower in repeated runs on the graph above. This remained reproducible after rebuilding the graph and refreshing statistics and the query cache.

I also reproduced the same behavior with a `COUNT { ... } > 0` input. That input is rewritten to `EXISTS`/`SemiApply`; its total DB Hits were 800,013 versus 18 with the CASE guard. This appears to be the same late-guarding issue, rather than a separate aggregation problem.

### Expected behavior

For anchor 1, the inexpensive condition is already false, so the high-cost subquery cannot affect whether the row passes `WHERE`. Applying that condition before `SemiApply` should avoid the unnecessary expansion, as the equivalent CASE plan demonstrates.

Could you please check whether the cheap predicate can be pushed before the correlated subquery in this form? Thank you for reviewing this report.
