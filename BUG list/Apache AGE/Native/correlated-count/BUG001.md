# Correlated COUNT rescans the same leaf table for each root

### Describe the situation

Hi, Apache AGE developers,

Please consider these two queries:

```sql
-- q1
SELECT * FROM ag_catalog.cypher('gsp_cases', $$
    MATCH (u:ProbeRoot)
    RETURN u.uid AS uid,
           COUNT {
               MATCH (x:ProbeLeaf)
               WHERE x.key=u.key AND x.mark=true
           } AS value
$$) AS (uid agtype, value agtype);

-- q2
SELECT * FROM ag_catalog.cypher('gsp_cases', $$
    MATCH (u:ProbeRoot)
    OPTIONAL MATCH (x:ProbeLeaf)
    WHERE x.key=u.key AND x.mark=true
    WITH u,count(x) AS value
    RETURN u.uid AS uid,value
$$) AS (uid agtype, value agtype);
```

I count the matching leaves in a subquery in q1 and use `OPTIONAL MATCH` with `count(x)` in q2. The second query groups by the root node before projecting its uid, and `count(x)` returns zero when the optional match finds no leaf. Both queries return the same 16 rows on the graph below, but AGE scans the leaf table once for each root in q1, and I measure about 15 times the runtime of q2.

### Which Apache AGE versions are affected?

I ran this case on Apache AGE 1.7.0 with PostgreSQL 18.1 (`Debian 18.1-1.pgdg13+2`), using Cypher through `ag_catalog.cypher()` in Docker on macOS ARM64.

### How to reproduce

Run the following SQL in an empty database, then run q1 and q2 above:

```sql
CREATE EXTENSION IF NOT EXISTS age;
LOAD 'age';
SET search_path = ag_catalog, "$user", public;

SELECT ag_catalog.create_graph('gsp_cases');
SELECT ag_catalog.create_vlabel('gsp_cases','ProbeRoot');
SELECT ag_catalog.create_vlabel('gsp_cases','ProbeLeaf');

INSERT INTO "gsp_cases"."ProbeRoot" (properties)
SELECT (jsonb_build_object('uid',i,'key',1)::text)::ag_catalog.agtype
FROM generate_series(1,16) AS s(i);

INSERT INTO "gsp_cases"."ProbeLeaf" (properties)
SELECT (jsonb_build_object('uid',i,'key',1,'mark',false)::text)::ag_catalog.agtype
FROM generate_series(1,100000) AS s(i);

INSERT INTO "gsp_cases"."ProbeLeaf" (properties)
VALUES ((jsonb_build_object('uid',100001,'key',1,'mark',true)::text)::ag_catalog.agtype);

CREATE INDEX "probe_cost_lookup"
ON "gsp_cases"."ProbeRoot" USING gin (properties);

CREATE INDEX "probe_cost_lookup_scalar"
ON "gsp_cases"."ProbeRoot" ((ag_catalog.agtype_access_operator(
    VARIADIC ARRAY[properties,'"uid"'::ag_catalog.agtype])));

VACUUM (ANALYZE) "gsp_cases"."ProbeRoot";
VACUUM (ANALYZE) "gsp_cases"."ProbeLeaf";
DISCARD PLANS;
```

All 16 roots have `key=1`. The leaf table contains 100,000 nodes with `mark=false` and one node with `mark=true`, all with the same key. Each root therefore has the same count of one.

For q1, I get 16 rows in columns `(uid, value)`: one `(i, 1)` row for each integer `i` from 1 through 16. Median runtime: **297.85 ms**.

For q2, I get the same 16 rows. Median runtime: **19.34 ms**.

I measured 40 paired runs across two fresh graph loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `EXPLAIN ANALYZE`; the median paired q1/q2 runtime ratio was **15.13×**, and the median paired runtime difference was **277.16 ms**.

Adding `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` before each SQL query gives these excerpts:

```text
q1:
Operator                         Actual Rows   Actual Loops   Rows Removed by Filter
Seq Scan on ProbeRoot                     16              1
  SubPlan 1: Aggregate                     1             16
    Seq Scan on ProbeLeaf                  1             16                   100000

q2:
Operator                         Actual Rows   Actual Loops   Rows Removed by Filter
Aggregate (strategy: Sorted)              16              1
  Hash Join (type: Right)                 16              1
    Seq Scan on ProbeLeaf                  1              1                   100000
    Hash                                  16              1
      Seq Scan on ProbeRoot               16              1
```

For q1, AGE executes the scalar aggregate 16 times and rechecks all 100,001 leaves on each call, although every root supplies the same key. For q2, it filters the leaf table once, joins the one matching leaf to the roots and groups the results. The `Rows Removed by Filter` value is per loop, so q1 rejects the same 100,000 false-mark leaves 16 times.

### Expected performance

Could AGE plan this correlated count with one filtered leaf scan and a join or reuse the count for the repeated key, as q2 does, so it avoids scanning the same leaves for each root?
