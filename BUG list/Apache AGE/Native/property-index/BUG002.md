# Redundant COALESCE prevents a property index lookup

> Current-version review (2026-10-31): **archived**. Submission target: PostgreSQL. Q1/Q2 median ordinary runtimes: **207.130 / 0.654 ms**, from 20 alternating paired runs after three warm-up pairs on one fresh graph. The original report graph scale was used. ### Describe the situation

Hi, Apache AGE developers,

Please consider these two queries:

```sql
-- q1
SELECT * FROM ag_catalog.cypher('gsp_cases', $$
    MATCH (n:ProbeNode)
    WHERE coalesce(n.id,null)=1
    RETURN n.uid AS uid
$$) AS (uid agtype);

-- q2
SELECT * FROM ag_catalog.cypher('gsp_cases', $$
    MATCH (n:ProbeNode {id:1})
    RETURN n.uid AS uid
$$) AS (uid agtype);
```

I wrap `n.id` in `coalesce(n.id,null)` in q1; this leaves its value unchanged. Both queries select the same node, but AGE leaves a single-argument `COALESCE` in q1's filter and scans the two-million-node table. For q2, it uses the existing property index, and I measure q1 taking about 300 times as long as q2.

### Which Apache AGE versions are affected?

I ran this case on Apache AGE 1.7.0 with PostgreSQL 18.1 (`Debian 18.1-1.pgdg13+2`), using Cypher through `ag_catalog.cypher()` in Docker on macOS ARM64.

### How to reproduce

Run the following SQL in an empty database, then run q1 and q2 above:

```sql
CREATE EXTENSION IF NOT EXISTS age;
LOAD 'age';
SET search_path = ag_catalog, "$user", public;

SELECT ag_catalog.create_graph('gsp_cases');
SELECT ag_catalog.create_vlabel('gsp_cases','ProbeNode');

INSERT INTO "gsp_cases"."ProbeNode" (properties)
SELECT (jsonb_build_object('uid',i,'id',i)::text)::ag_catalog.agtype
FROM generate_series(1,2000000) AS s(i);

CREATE INDEX "probe_cost_lookup"
ON "gsp_cases"."ProbeNode" USING gin (properties);

CREATE INDEX "probe_cost_lookup_scalar"
ON "gsp_cases"."ProbeNode" ((ag_catalog.agtype_access_operator(
    VARIADIC ARRAY[properties,'"id"'::ag_catalog.agtype])));

VACUUM (ANALYZE) "gsp_cases"."ProbeNode";
DISCARD PLANS;
```

The nodes have integer `id` values from 1 through 2,000,000, and each node has the same value in `uid`. Only one node has `id=1`. Both indexes are ready and valid before I run the queries.

For q1, I get one row: `uid=1`. Median runtime: **145.97 ms**.

For q2, I get the same row. Median runtime: **0.50 ms**.

I measured 40 paired runs across two fresh graph loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `EXPLAIN ANALYZE`; the median paired q1/q2 runtime ratio was **299.59×**, and the median paired runtime difference was **145.46 ms**.

Adding `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` before each SQL query gives these excerpts:

```text
q1:
Gather
  Actual Rows: 1
  Actual Loops: 1
  Workers Planned: 2
  Workers Launched: 2
  Seq Scan on ProbeNode
    Parallel Aware: true
    Actual Rows: 0.33
    Actual Loops: 3
    Rows Removed by Filter: 666666
    Filter: (COALESCE(agtype_access_operator(VARIADIC ARRAY[properties, '"id"'::agtype])) = '1'::agtype)

q2:
Bitmap Heap Scan on ProbeNode
  Actual Rows: 1
  Actual Loops: 1
  Recheck Cond: (properties @> '{"id": 1}'::agtype)
  Bitmap Index Scan on probe_cost_lookup
    Actual Rows: 1
    Actual Loops: 1
    Index Cond: (properties @> '{"id": 1}'::agtype)
```

For q1, AGE removes the trailing NULL argument but retains `COALESCE` around the property access, so it checks the table with a parallel sequential scan. PostgreSQL reports scan row counts as averages across the three loops; `666666` is the rounded per-loop average of rejected rows, and the `Gather` returns one row. For q2, it uses the GIN index to read the one matching node.

### Expected performance

Could AGE remove the redundant single-argument `COALESCE` so the property condition can use an existing index instead of scanning the whole table, as q2 does?
