# Issue 报告写作规则

本规则适用于 `BUG list/` 及其所有子目录中的 issue 报告。以后新增、修改或润色报告都必须遵循本规则；用户对具体报告的新要求优先。

报告用英文，面向数据库开发者。沿用 SCor 原始 GitHub 报告的段落安排和表达重点：展示查询对，给出复现、结果与耗时，用执行计划说明多做了什么，最后提出优化请求。正文要像开发者报告问题，说清楚发生了什么。

## 固定结构与段落顺序

报告使用一个具体、简短的英文标题，正文只保留以下四节。将 `<DBMS>` 换成实际数据库名称。

### 1. `Describe the situation`

- 用 `Hi, <DBMS> developers,` 问候。
- 用 `Please consider these two queries:` 引出 `q1`、`q2`，在代码块中给出完整查询。
- 查询只写一次。后面的复现步骤引用上方的 `q1`、`q2`。
- 查询后用一个短段落，通常两到四句，说明两种写法的差别、相同的结果，以及慢查询多做了什么。可以用一句话给出约多少倍的耗时差距。
- 从具体查询和数据入手，不先介绍测试框架、方法贡献或数据库背景。

### 2. `Which <DBMS> versions are affected?`

- 用一个短段落列出已经实测的版本、版本类别、查询语言版本和运行环境。
- 与问题有关且有记录支持时，补充规划器、执行引擎或设置。
- 只声称测试过的版本。不要把单个版本的结果写成“所有版本”或未经核查的“最新版”。

### 3. `How to reproduce`

按以下顺序写，不另拆 `Observed performance` 或 `Additional context` 等章节：

1. 给出从空数据库开始的完整建图或建表语句，包括数据、索引及必要设置。让读者创建数据后运行上方的 `q1`、`q2`。
2. 用短段落说明与问题有关的数据特点，例如哪个节点的条件为 false、它后面有多少分支、哪个节点提供有效结果。
3. 分别写出 `q1`、`q2` 的实际返回值和实际耗时。例如：`For q1, I get one row: ... Median runtime: ...`；紧接着给出 `q2` 的结果和耗时。不要用一张总表代替这两个段落。
4. 用一到两句话说明必要的计时口径和耗时倍率。正文只保留重复次数、预热、完整结果读取及是否使用 `PROFILE` 等与理解数字有关的信息。
5. 随后给出实际执行计划或 `PROFILE` 摘录。摘录必须标明为 excerpt，保留能说明问题的算子、行数和工作量字段。
6. 在计划后用一个短段落解释差距：慢查询先做了什么、多访问了哪些数据；另一条查询在哪一步跳过这些工作。原因解释只写一次。

### 4. `Expected performance`

- 用一句话提出明确的优化请求：希望数据库跳过哪部分工作，现有的另一条查询怎样做到这一点。
- 根据已经观察到的低成本行为提出请求，不编造修复后的耗时。
- 不把两条语义等价查询的执行时间必须相同写成保证，也不把某个执行顺序写成数据库必须遵守的语义要求。

## 表达要求

- 用 `I`、`you` 和具体操作说话。优先写“我运行了什么、得到什么、数据库访问了哪些数据”。
- 用短句说明具体事实。避免反复使用 `semantically equivalent`、`decisive guard`、`high-cost branch`、`confirmation protocol` 等抽象标签来代替解释。
- 保留查询、算子和字段的原名，例如 `EXISTS`、`VarLengthExpand`、`keep`；这些名称能帮助开发者定位问题。
- 不写论文式的符号推导、TRUE/FALSE/NULL 公式展开、框架介绍、贡献陈述或无依据的生产场景。影响结论的语义前提要用普通语言留在正文。
- 删除套话、夸张判断和重复论证。不要在开头、计划解释和预期性能中重复同一套原因分析。
- 不追加扩展规模、其他语法变体、长篇测量协议、安装教程或工程文件清单。只保留复现当前问题所需的材料。
- 不强行凑句数，不加入破折号式转折、排比或总结口号。沿用 stop-slop 的表达要求。

## 查询、计时与证据要求

- `q1`、`q2` 必须与对应的计时记录一致。可以调整空白和排版；改动括号、变量名或子表达式后，必须重新核对对应证据，不能直接沿用旧数字。
- 运行时间、结果和计划必须对应复现代码中的同一数据规模、参数和数据状态。正文写明与问题有关的分支或噪声数量，不强制列节点总数表。
- 核对完整查询结果，包括重复行或路径、NULL、空输入和返回字段。说明当前数据上的一致结果；声称两条查询语义等价时，还要有相应的语义依据。
- 只有实际测量过才写运行时间（runtime）。使用中位数就标明 `Median runtime`；使用单次测量就如实说明。次数、预热和统计口径都来自当前记录，不能套用样稿中的 40 次或其他数字。
- 区分普通查询计时与 `PROFILE` 计时。DB Hits、Rows 等说明执行工作量，不能当作耗时或耗时倍率。
- 写清倍率方向，例如 `q2/q1`。配对测量使用每对耗时比的中位数时，要说明是 paired runs；不要将它写成两项耗时中位数的商。可用约数概述，保留精确统计口径供核查。
- 查询取消或超时时，写明实际等待时间、超时阈值及由此支持的时间下界；不能把未完成的执行写成完整耗时，也不能将下界写成确定倍率。
- 使用当前数据库实际支持的计划或分析工具；`PROFILE` 是现有 Neo4j 样稿的做法，不是其他数据库的必需语法。
- 不把推算的预期耗时、改写后的示意输出或人为排版的结果冒充真实控制台日志。正文可以直接陈述测量结果；计划字段重排后必须标为摘录。
- 用实际计划和执行工作量支撑“多做了无必要工作”的判断。只有耗时差异时，不把原因写成已经确认的优化遗漏。
- 在文末 HTML 注释中保留本地来源：查询与数据文件、运行时间原始记录、完整测量协议和计划记录。正文仍须交代计时边界，并提供足够的复现信息；不能让读者依赖隐藏注释理解报告。

## 交付前核对

- 四节标题和段落顺序正确；读者能创建数据并运行查询。
- 查询、返回值、版本、时间、倍率和执行计划都能对应到原始证据。
- 报告说明了相同结果、额外工作和期望跳过的操作。
- 删掉附加案例、重复解释和实验总结式段落，再读一遍确认是在向开发者报告一个具体问题。
