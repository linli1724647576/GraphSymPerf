## Describe the situation

Hi, HugeGraph developers,

## Which HugeGraph versions are affected?

I reproduced this on Apache HugeGraph 1.7.0 with Apache TinkerPop 3.5.1, using Gremlin-Groovy over HTTP and RocksDB in an ARM64 Docker container on macOS. The measured JVM used `-Xms512m -Xmx3685m`; client and server evaluation limits were 30 seconds.

The `GspLow` vertex with `uid=1` has a valid two-edge trail through `GspMiddle(uid=2)` to `GspHigh(uid=3)`. It also connects to `GspBad(uid=0, keep=false)`. Beyond that vertex are 200 separate Middle-to-High branches. All other vertices have `keep=true`. The edge-identity check preserves TRAIL semantics, including distinct parallel edges, and allows vertex revisits.

Both queries apply the all-node check after `RepeatStep`; the check itself stops at the first false node. In q2, the 200 branch High vertices each reach the shared Bad vertex and then produce 200 further trails, including trails into the other Middle branches. Those 40,000 extensions cannot contribute a passing result because their prefix already contains `keep=false`. q1 starts at the single Low vertex and avoids this quadratic combination of branch starts and continuations, although it also checks completed paths. This is a request to recognize the monotone path predicate across `repeat`, path-node projection and the later filter; the measured q2/q1 ratio is not a measured speedup from a pruning patch.

## Expected performance

Please stop extending a path when its prefix contains a node with `keep=false`, while preserving TRAIL semantics, so q2 can skip the rejected combinations that q1 avoids through its starting endpoint.
