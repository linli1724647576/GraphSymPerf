# A redundant null test prevents the count-to-existence optimization

## Describe the situation

Hi, Apache HugeGraph developers,

Please consider these two queries:

```groovy
// q1
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.outE('GSP_SC_HIGH')
            .count()
            .is(P.neq(null))
            .is(P.gt(0))
    )
    .project('uid')
    .by(__.values('uid'))

// q2
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.outE('GSP_SC_HIGH')
            .count()
            .is(P.gt(0))
    )
    .project('uid')
    .by(__.values('uid'))
```

Both queries return `[[uid:1]]`. The only change is testing the count against null before testing it against zero. `count()` returns a non-null integer, including zero, so this additional test changes neither the result nor the traversal order. With 400000 HIGH edges, q1 is about 123 times slower than q2 in paired runs.

## Which Apache HugeGraph versions are affected?

I tested Apache HugeGraph 1.7.0 with its TinkerPop 3.5.1 Gremlin-Groovy engine, the RocksDB backend, and OpenJDK 11.0.30 in a local Docker container.

## How to reproduce

Start with an empty graph and bind its traversal source to `g`. Create the schema, index, and data:

```groovy
// Start with an empty HugeGraph graph and no conflicting schema.
// The native traversal source for this graph is already bound to g.
def graph = g.getGraph()
def s = graph.schema()
long n = 100000L
long highCount = 4L * n
long firstUid = 680488L

['uid', 'id', 'key', 'expected_count', '_gsp_edge_ordinal'].each { name ->
    s.propertyKey(name)
        .asLong()
        .valueSingle()
        .create()
}
s.propertyKey('mark')
    .asBoolean()
    .valueSingle()
    .create()
s.vertexLabel('ScorRoot')
    .useCustomizeStringId()
    .properties('uid', 'id', 'key', 'expected_count')
    .nullableKeys('uid', 'id', 'key', 'expected_count')
    .create()
s.vertexLabel('ScorTarget')
    .useCustomizeStringId()
    .properties('uid', 'mark', 'key')
    .nullableKeys('uid', 'mark', 'key')
    .create()
['GSP_SC_HIGH', 'GSP_SC_REF'].each { name ->
    s.edgeLabel(name)
        .link('ScorRoot', 'ScorTarget')
        .multiTimes()
        .properties('_gsp_edge_ordinal')
        .sortKeys('_gsp_edge_ordinal')
        .create()
}
s.indexLabel('gsp_cost_lookup_ScorRoot_id')
    .onV('ScorRoot')
    .by('id')
    .secondary()
    .create()

def root = g.addV('ScorRoot')
    .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorRoot:1')
    .next()
root.property('uid', 1L)
root.property('id', 1L)
root.property('key', 1L)
root.property('expected_count', highCount)
long written = 1L
for (long i = 0L; i < highCount; i++) {
    long uid = firstUid + i
    def v = g.addV('ScorTarget')
        .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorTarget:' + uid)
        .next()
    v.property('uid', uid)
    v.property('mark', true)
    v.property('key', 1L)
    if (++written % 250L == 0L) graph.tx().commit()
}
for (long uid = 2L; uid <= 4L; uid++) {
    def v = g.addV('ScorTarget')
        .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorTarget:' + uid)
        .next()
    v.property('uid', uid)
    v.property('mark', true)
    v.property('key', 1L)
    if (++written % 250L == 0L) graph.tx().commit()
}
graph.tx().commit()

written = 0L
for (long i = 0L; i < highCount; i++) {
    def a = g.V('ScorRoot:1').next()
    def b = g.V('ScorTarget:' + (firstUid + i)).next()
    a.addEdge('GSP_SC_HIGH', b, '_gsp_edge_ordinal', i)
    if (++written % 250L == 0L) graph.tx().commit()
}
for (long uid = 2L; uid <= 4L; uid++) {
    def a = g.V('ScorRoot:1').next()
    def b = g.V('ScorTarget:' + uid).next()
    a.addEdge('GSP_SC_REF', b, '_gsp_edge_ordinal', highCount + uid - 2L)
    if (++written % 250L == 0L) graph.tx().commit()
}
graph.tx().commit()
```

The indexed `ScorRoot.id=1` node has 400000 outgoing HIGH edges. Neither query returns the count or has side effects; the child traversal is only used to test whether an edge exists.

For q1, I get `[[uid:1]]`. Median runtime: **250.27 ms**.

For q2, I get `[[uid:1]]`. Median runtime: **1.97 ms**.

I fully consumed both results in 40 paired runs across two independently cleared and rebuilt graphs, after three warm-up pairs per graph. The median paired q1/q2 ratio is **122.69**, with a bootstrap 95% interval of **[110.16, 138.24]**; the median paired difference is **248.31 ms**. These are ordinary query times; profiling was separate.

Actual `explain()` excerpts after `CountStrategy`:

```text
q1 child:
  TraversalFilterStep([VertexStep(OUT,[GSP_SC_HIGH],edge),
                       CountGlobalStep, IsStep(neq), IsStep(gt(0))])
q2 child:
  TraversalFilterStep([VertexStep(OUT,[GSP_SC_HIGH],edge)])
```

Actual `profile()` excerpts from the same confirmation graph, with duration in milliseconds:

```text
q1 child:
HugeVertexStep(OUT,[GSP_SC_HIGH],edge)
  counts={traverserCount:400000, elementCount:400000}, dur=259.091477
CountGlobalStep
  counts={traverserCount:1, elementCount:1}, dur=30.052316
IsStep(neq)
IsStep(gt(0))

q2:
TraversalFilterStep([HugeVertexStep(OUT,[GSP_SC_HIGH],edge)])
  counts={traverserCount:1, elementCount:1}, dur=0.327749
  HugeVertexStep(OUT,[GSP_SC_HIGH],edge)
    counts={}, dur=0.303875
```

The [existing `CountStrategy`](https://raw.githubusercontent.com/apache/tinkerpop/3.5.1/gremlin-core/src/main/java/org/apache/tinkerpop/gremlin/process/traversal/strategy/optimization/CountStrategy.java) removes q2's count and zero test, leaving an existence filter. In q1, the intervening null test prevents that rewrite, and `CountGlobalStep` consumes all 400000 edge traversers although the exact count is never observed. q2's profile does not report the child step's input-edge count, so I am not claiming that its storage backend reads exactly one edge.

## Expected performance

Could you simplify the always-true null test on `count()` and apply the existing count-to-existence optimization, so q1 can avoid consuming every edge just as q2 already does?
