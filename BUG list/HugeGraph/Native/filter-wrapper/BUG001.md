# A filter wrapper prevents an early root check

## Describe the situation

Hi, Apache HugeGraph developers,

Please consider these two queries:

```groovy
// q1
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.out('GSP_SC_HIGH')
            .has('mark', false)
    )
    .filter(__.has('id', 0))
    .project('uid')
    .by(__.values('uid'))

// q2
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.out('GSP_SC_HIGH')
            .has('mark', false)
    )
    .has('id', 0)
    .project('uid')
    .by(__.values('uid'))
```

Both queries return an empty list. The only change is wrapping the same `has('id',0)` test in `filter`; the written filter order is unchanged. With 120000 outgoing HIGH edges, q1 is about 101 times slower than q2 in paired runs.

## Which Apache HugeGraph versions are affected?

I tested Apache HugeGraph 1.7.0 with its TinkerPop 3.5.1 Gremlin-Groovy engine, the RocksDB backend, and OpenJDK 11.0.30 in a local Docker container.

## How to reproduce

Start with an empty graph and bind its traversal source to `g`. Create the schema, index, and data:

```groovy
// Start with an empty HugeGraph graph and no conflicting schema.
// The native traversal source for this graph is already bound to g.
def graph = g.getGraph()
def s = graph.schema()
long n = 30000L
long highCount = 4L * n
long firstUid = 680488L

['uid', 'id', 'key', 'expected_count', '_gsp_edge_ordinal'].each { name ->
    s.propertyKey(name)
        .asLong()
        .valueSingle()
        .create()
}
s.propertyKey('mark')
    .asBoolean()
    .valueSingle()
    .create()
s.vertexLabel('ScorRoot')
    .useCustomizeStringId()
    .properties('uid', 'id', 'key', 'expected_count')
    .nullableKeys('uid', 'id', 'key', 'expected_count')
    .create()
s.vertexLabel('ScorTarget')
    .useCustomizeStringId()
    .properties('uid', 'mark', 'key')
    .nullableKeys('uid', 'mark', 'key')
    .create()
['GSP_SC_HIGH', 'GSP_SC_REF'].each { name ->
    s.edgeLabel(name)
        .link('ScorRoot', 'ScorTarget')
        .multiTimes()
        .properties('_gsp_edge_ordinal')
        .sortKeys('_gsp_edge_ordinal')
        .create()
}
s.indexLabel('gsp_cost_lookup_ScorRoot_id')
    .onV('ScorRoot')
    .by('id')
    .secondary()
    .create()

def root = g.addV('ScorRoot')
    .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorRoot:1')
    .next()
root.property('uid', 1L)
root.property('id', 1L)
root.property('key', 1L)
root.property('expected_count', highCount)
long written = 1L
for (long i = 0L; i < highCount; i++) {
    long uid = firstUid + i
    def v = g.addV('ScorTarget')
        .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorTarget:' + uid)
        .next()
    v.property('uid', uid)
    v.property('mark', true)
    v.property('key', 1L)
    if (++written % 250L == 0L) graph.tx().commit()
}
for (long uid = 2L; uid <= 4L; uid++) {
    def v = g.addV('ScorTarget')
        .property(org.apache.tinkerpop.gremlin.structure.T.id, 'ScorTarget:' + uid)
        .next()
    v.property('uid', uid)
    v.property('mark', true)
    v.property('key', 1L)
    if (++written % 250L == 0L) graph.tx().commit()
}
graph.tx().commit()

written = 0L
for (long i = 0L; i < highCount; i++) {
    def a = g.V('ScorRoot:1').next()
    def b = g.V('ScorTarget:' + (firstUid + i)).next()
    a.addEdge('GSP_SC_HIGH', b, '_gsp_edge_ordinal', i)
    if (++written % 250L == 0L) graph.tx().commit()
}
for (long uid = 2L; uid <= 4L; uid++) {
    def a = g.V('ScorRoot:1').next()
    def b = g.V('ScorTarget:' + uid).next()
    a.addEdge('GSP_SC_REF', b, '_gsp_edge_ordinal', highCount + uid - 2L)
    if (++written % 250L == 0L) graph.tx().commit()
}
graph.tx().commit()
```

The root has SINGLE-valued `id=1`, so `id=0` cannot match it. Its 120000 HIGH neighbors all have `mark=true`, so the outgoing traversal filter also has no match. The `ScorRoot.id` secondary index is in `CREATED` status.

For q1, I get `[]`. Median runtime: **146.50 ms**.

For q2, I get `[]`. Median runtime: **1.48 ms**.

I fully consumed both results in 40 paired runs across two independently cleared and rebuilt graphs, after three warm-up pairs per graph. The median paired q1/q2 ratio is **100.93**, with a bootstrap 95% interval of **[94.38, 107.54]**; the median paired difference is **145.01 ms**. These are ordinary query times; profiling was separate.

Actual `explain()` excerpt for q1:

```text
After FilterRankingStrategy:
  ... TraversalFilterStep([VertexStep(OUT,[GSP_SC_HIGH],vertex), HasStep([mark.eq(false)])])
      TraversalFilterStep([HasStep([id.eq(0)])]) ...
After InlineFilterStrategy:
  ... TraversalFilterStep([VertexStep(OUT,[GSP_SC_HIGH],vertex), HasStep([mark.eq(false)])])
      HasStep([id.eq(0)]) ...
```

Actual `profile()` excerpts from the same confirmation graph, with duration in milliseconds:

```text
q1:
HugeGraphStep(Vertex,[~label.eq(ScorRoot), id.eq(1)])
  counts={traverserCount:1, elementCount:1}
TraversalFilterStep([HugeVertexStep(OUT,[GSP_SC_HIGH],Vertex,[mark.eq(false)])])
  dur=147.530709, counts={}
  HugeVertexStep(OUT,[GSP_SC_HIGH],Vertex,[mark.eq(false)])
    dur=147.500667, counts={}
HasStep([id.eq(0)])

q2:
HugeGraphStep(Vertex,[~label.eq(ScorRoot), id.eq(1), id.eq(0)])
  counts={}
TraversalFilterStep([HugeVertexStep(OUT,[GSP_SC_HIGH],Vertex,[mark.eq(false)])])
  HugeVertexStep(OUT,[GSP_SC_HIGH],Vertex,[mark.eq(false)])
    dur=0.0, counts={}
```

`FilterRankingStrategy` runs before the wrapper is removed by `InlineFilterStrategy`, leaving q1's root test after the outgoing traversal. The plain test in q2 is moved and folded into `HugeGraphStep`, which rejects the root before expansion. In q1, HugeGraph's [adjacent-vertex filtering implementation](https://raw.githubusercontent.com/apache/hugegraph/1.7.0/hugegraph-server/hugegraph-core/src/main/java/org/apache/hugegraph/traversal/optimize/HugeVertexStep.java) filters the neighboring vertices; on this graph it must exhaust the neighborhood to establish that no `mark=false` neighbor exists. The fused step's profile does not expose an input-edge count, so its empty `counts` map is not evidence of zero backend reads.

## Expected performance

Could you move the root test before the outgoing traversal after removing the wrapper, so q1 can skip the neighbor filtering just as q2 already does?
