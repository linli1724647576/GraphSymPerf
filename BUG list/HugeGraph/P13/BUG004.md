# Independent optional traversals repeat the same high-degree branch

> Current-version review (2026-10-31): **archived**. Submission target: Apache TinkerPop traversal order. I evaluate two read-only optional branches from each anchor in opposite orders. The HIGH branch only reads the anchor and does not depend on the LOW result. Both queries return the same ten rows, including two rows with nulls, but q1 takes about 7.34 times as long because it repeats the HIGH traversal after LOW has produced multiple rows.

### Which HugeGraph versions are affected?

I reproduced this on Apache HugeGraph 1.7.0 with Apache TinkerPop 3.5.1, using Gremlin-Groovy over HTTP and RocksDB in an ARM64 Docker container on macOS. The measured JVM used `-Xms512m -Xmx3685m`; client and server evaluation limits were 30 seconds.

In q1, LOW produces eight rows for anchor 1 before HIGH runs. `CoalesceStep` runs its HIGH child for each incoming row, so it repeats the same 8,001-neighbor search eight times and also reads anchor 3's one HIGH neighbor. In q2, HIGH runs once per anchor before LOW multiplies the passing row. Its 8,002 HIGH outputs contrast with q1's 64,009. The HIGH traversal reads no LOW binding and does not modify the graph; avoiding this repeated computation can preserve the result multiplicities and nulls. q2 achieves this through branch order, not through a demonstrated cache or an implemented reordering rule.

### Expected performance

Please avoid repeating the independent HIGH computation for the same anchor after LOW multiplies its rows, as q2 avoids that work by evaluating HIGH first, while preserving all duplicate and null-extended rows.
