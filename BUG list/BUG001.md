# Semantically equivalent comma-pattern reorder inflates all-node scan work

I found that reordering two comma-separated patterns inside the same `MATCH` clause changes the execution plan and increases PROFILE database accesses, although the two queries are semantically equivalent and return the same result.

**Neo4j Version:** 2026.04.0 community
**Operating System:** macOS 26.3.1 arm64
**Installation Method:** Docker image `neo4j:2026.04.0-community`
**API/Driver:** Cypher Shell

### Steps to reproduce

1. Load the attached graph setup file into an empty disposable database:

```bash
cypher-shell -u neo4j -p <password> -d neo4j -f reproducer_graph.cypher.txt
```

2. Verify the graph size:

```cypher
MATCH (n) RETURN count(n) AS nodes;
-- nodes: 1280

MATCH ()-[r]->() RETURN count(r) AS relationships;
-- relationships: 2290
```

3. Verify the query-relevant schema and distribution:

```cypher
SHOW INDEXES
YIELD name, entityType, labelsOrTypes, properties
RETURN name, entityType, labelsOrTypes, properties
ORDER BY name;
-- Relevant result:
-- i0 NODE ["T5"] ["k63"]
-- i1 NODE ["T1"] ["k38"]
-- i2 NODE ["L1"] ["k10"]
-- i3 NODE ["T1"] ["k35"]
-- i4 NODE ["T0"] ["k32"]
-- i5 NODE ["L0"] ["k2"]
-- i6 NODE ["L0"] ["k4"]
-- No index is defined for L3, L4, T3, r4.id, r5.id, or r4.k48.

MATCH (n)
UNWIND labels(n) AS label
RETURN label, count(*) AS nodes
ORDER BY label;
-- L0: 290, L1: 390, L2: 410, L3: 360, L4: 350

MATCH ()-[r]->()
RETURN type(r) AS type, count(*) AS relationships
ORDER BY type;
-- T0: 400, T1: 300, T2: 360, T3: 460, T4: 390, T5: 380

MATCH (n0:L3)-[r4:T3]->(n6)<-[r5:T3]-(n7:L4)
WHERE r4.id <> r5.id
RETURN count(*) AS relationshipPatternRows;
-- relationshipPatternRows: 80
```

4. Run the base query:

```cypher
PROFILE
MATCH (n2)
WITH *
WITH max('J') AS a0, n2
ORDER BY a0
WHERE (276190253 > -71315356)
MATCH (n0 :L3)-[r4 :T3]->(n6)<-[r5 :T3]-(n7 :L4), (n5)
WHERE (('3B' CONTAINS a0) AND ((r4.id) <> (r5.id)))
WITH DISTINCT (r4.k48) AS a1
WHERE a1
RETURN min('R') AS a2
ORDER BY a2;
```

5. Run the transformed query:

```cypher
PROFILE
MATCH (n2)
WITH *
WITH max('J') AS a0, n2
ORDER BY a0
WHERE (276190253 > -71315356)
MATCH (n5), (n0 :L3)-[r4 :T3]->(n6)<-[r5 :T3]-(n7 :L4)
WHERE (('3B' CONTAINS a0) AND ((r4.id) <> (r5.id)))
WITH DISTINCT (r4.k48) AS a1
WHERE a1
RETURN min('R') AS a2
ORDER BY a2;
```

### Expected behavior

The transformed query only reorders two comma-separated pattern atoms inside the same `MATCH` clause:

```cypher
MATCH (n0:L3)-[r4:T3]->(n6)<-[r5:T3]-(n7:L4), (n5)
MATCH (n5), (n0:L3)-[r4:T3]->(n6)<-[r5:T3]-(n7:L4)
```

These two forms should be semantically equivalent. The `WHERE` clause remains attached to the same `MATCH` clause, the independent node pattern `(n5)` shares no variables with the relationship pattern, and `n5` is not referenced by `WHERE`, `WITH`, `RETURN`, or `ORDER BY`. Therefore, reordering the two pattern atoms should preserve the result and should not trigger a large execution-plan regression.

This case does not swap schema roles. Both queries use the same `L3` label, `T3` relationship type, and `L4` label in the same directions over the same loaded graph. The only moved atom is the independent unlabeled node pattern `(n5)`, whose cardinality is 1,280 in both forms. The distribution check above rules out a different label or relationship distribution between two symmetric schema roles as the cause of the regression.

The transformed query is `206.34x` slower and performs `293.04x` more database accesses, although it is semantically equivalent to the base query.

The profile rows match the distribution sanity check. Under the 1,280-row outer input from `MATCH (n2)`, `NodeByLabelScan n0:L3` produces `1,280 * 360 = 460,800` rows, and the relationship pattern after `r4.id <> r5.id` produces `1,280 * 80 = 102,400` rows. In the transformed plan, `AllNodesScan n5` is executed after those 102,400 rows and before the independent `$autostring_1 CONTAINS a0` filter, producing `102,400 * 1,280 = 131,072,000` rows. In the base plan, the same filter is applied before the expensive relationship expansions and before the independent `(n5)` scan, so those downstream operators produce zero rows.
