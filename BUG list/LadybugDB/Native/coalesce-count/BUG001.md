# COALESCE executes a COUNT subquery after a non-NULL constant

### Describe the situation

Hi, LadybugDB developers,

Please consider these two queries:

```cypher
// q1
MATCH (u:ProbeRoot {uid:1})
RETURN coalesce(0, COUNT {
    MATCH (u)-[:ProbeA]->(m:ProbeMid)-[:ProbeB]->(h:ProbeHub)-[:ProbeC]->(l:ProbeLeaf)
    WHERE m.uid <> l.uid
}) AS value;

// q2
MATCH (u:ProbeRoot {uid:1})
RETURN 0 AS value;
```

The first `COALESCE` argument is the non-NULL integer zero, so the count cannot change the result. I get `value=0` from both queries, but LadybugDB executes the count subquery in q1 and processes 2,250,000 matching paths. I measure q1 taking about 745 times as long as q2.

### Which LadybugDB versions are affected?

I ran this case on LadybugDB 0.21.2 with Cypher through its Python driver on macOS ARM64.

### How to reproduce

Create the following tables and graph in an empty database, then run q1 and q2 above:

```cypher
CREATE NODE TABLE ProbeRoot(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeMid(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeHub(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeLeaf(uid INT64 PRIMARY KEY, keep BOOLEAN);

CREATE REL TABLE ProbeA(FROM ProbeRoot TO ProbeMid);
CREATE REL TABLE ProbeB(FROM ProbeMid TO ProbeHub);
CREATE REL TABLE ProbeC(FROM ProbeHub TO ProbeLeaf);

CREATE (:ProbeRoot {uid:1,keep:true}), (:ProbeHub {uid:1,keep:true});

MATCH (u:ProbeRoot {uid:1}), (h:ProbeHub {uid:1})
UNWIND range(1,1500) AS i
CREATE (u)-[:ProbeA]->(m:ProbeMid {uid:i,keep:true})-[:ProbeB]->(h);

MATCH (h:ProbeHub {uid:1})
UNWIND range(1,1500) AS i
CREATE (h)-[:ProbeC]->(:ProbeLeaf {uid:1000000+i,keep:true});
```

The root connects to 1,500 middle nodes, each middle node connects to the same hub, and the hub connects to 1,500 leaves. The graph has 3,002 nodes and 4,500 edges. Each middle-node uid differs from each leaf uid, so all 2,250,000 three-hop paths satisfy the count predicate.

For q1, I get one row: `value=0`. Median runtime: **131.45 ms**.

For q2, I get the same row. Median runtime: **0.18 ms**.

I measured 40 paired runs across two fresh database loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `PROFILE`; the median paired q1/q2 runtime ratio was **744.88×**, and the median paired runtime difference was **131.28 ms**.

Adding `PROFILE` gives these excerpts from the native `NumOutputTuples` fields:

For q1, LadybugDB follows the three relationship tables, evaluates the inequality for all 2,250,000 paths and joins the aggregate count back to the root before projecting zero. For q2, it reads the root through its primary-key index and projects zero without executing the traversal or aggregate.

### Expected performance

Could LadybugDB skip the COUNT subquery after the first non-NULL `COALESCE` argument, so q1 reads only the root and returns zero as q2 does?
