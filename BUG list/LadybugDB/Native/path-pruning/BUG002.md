# ALL over path nodes misses pruning in the recursive traversal

### Describe the situation

Hi, LadybugDB developers,

Please consider these two queries:

```cypher
// q1
MATCH p=(u:ProbeRoot {uid:1})-[:ProbeA|ProbeB|ProbeC* TRAIL 3..3]->(v:ProbeLeaf)
WHERE all(n IN nodes(p) WHERE n.keep=true)
RETURN u.uid AS root_uid, v.uid AS leaf_uid, length(p) AS hops;

// q2
MATCH p=(u:ProbeRoot {uid:1})-
    [:ProbeA|ProbeB|ProbeC* TRAIL 3..3 (e,n | WHERE n.keep=true)]->(v:ProbeLeaf)
WHERE u.keep=true
RETURN u.uid AS root_uid, v.uid AS leaf_uid, length(p) AS hops;
```

Both queries use the same three-hop `TRAIL` pattern and require `keep=true` on every path node. In q2, I put the node condition inside the recursive relationship and check the starting node with `u.keep=true`. Both return no rows on the graph below, but q1 constructs one million paths before rejecting them, and I measure about 308 times the runtime of q2.

### Which LadybugDB versions are affected?

I ran this case on LadybugDB 0.21.2 with Cypher through its Python driver on macOS ARM64.

### How to reproduce

Create the following tables and graph in an empty database, then run q1 and q2 above:

```cypher
CREATE NODE TABLE ProbeRoot(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeMid(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeHub(uid INT64 PRIMARY KEY, keep BOOLEAN);
CREATE NODE TABLE ProbeLeaf(uid INT64 PRIMARY KEY, keep BOOLEAN);

CREATE REL TABLE ProbeA(FROM ProbeRoot TO ProbeMid);
CREATE REL TABLE ProbeB(FROM ProbeMid TO ProbeHub);
CREATE REL TABLE ProbeC(FROM ProbeHub TO ProbeLeaf);

CREATE (:ProbeRoot {uid:1,keep:true}), (:ProbeHub {uid:1,keep:false});

MATCH (u:ProbeRoot {uid:1}), (h:ProbeHub {uid:1})
UNWIND range(1,1000) AS i
CREATE (u)-[:ProbeA]->(m:ProbeMid {uid:i,keep:true})-[:ProbeB]->(h);

MATCH (h:ProbeHub {uid:1})
UNWIND range(1,1000) AS i
CREATE (h)-[:ProbeC]->(:ProbeLeaf {uid:1000000+i,keep:true});
```

The root connects to 1,000 middle nodes, each middle node connects to the same hub, and the hub connects to 1,000 leaves. The graph has 2,002 nodes and 3,000 edges. Every three-hop path goes through the hub with `keep=false`, so none of the one million paths can satisfy either query.

For q1, I get no rows. Median runtime: **607.43 ms**.

For q2, I get no rows. Median runtime: **1.97 ms**.

I measured 40 paired runs across two fresh database loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `PROFILE`; the median paired q1/q2 runtime ratio was **307.99×**, and the median paired runtime difference was **605.53 ms**.

Adding `PROFILE` gives these excerpts from the native `NumOutputTuples` fields:


Both plans use `VAR_LEN_JOINS`; the `READ_FTABLE` operators expose the generated path rows from its internal table. For q1, LadybugDB reads one million path rows and checks `ALL` after expansion. For q2, it excludes the hub through the node filter and `SEMI_MASKER` before recursion, and the path reader returns zero rows. It still scans node data to prepare the filters, but avoids constructing the paths through the false hub.

### Expected performance

Could LadybugDB push this node-only `ALL` condition into the recursive traversal, as q2 does, so it excludes the false hub before constructing the paths behind it?
