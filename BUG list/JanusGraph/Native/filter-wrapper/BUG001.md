# A wrapped vertex filter misses early rejection

> Current-version review (2026-10-31): **draft**. Submission target: Apache TinkerPop. Q1/Q2 median ordinary runtimes: **284.861 / 1.720 ms**, from 20 alternating paired runs after three warm-up pairs on one fresh graph. The original report graph scale was used. ### Describe the situation

Hi, JanusGraph developers,

Please consider these two queries:

```groovy
// q1
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.out('GSP_SC_HIGH')
            .has('mark', false)
    )
    .filter(__.has('id', 0))
    .project('uid')
    .by(__.values('uid'))

// q2
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .filter(
        __.out('GSP_SC_HIGH')
            .has('mark', false)
    )
    .has('id', 0)
    .project('uid')
    .by(__.values('uid'))
```

I wrap the last `has('id',0)` in `filter()` in q1. Both queries return no rows: `id` has SINGLE cardinality, so the starting vertex cannot satisfy both `id=1` and `id=0`. On the graph below, q1 takes about 201 times as long as q2.

### Which JanusGraph versions are affected?

I tested JanusGraph 1.1.0 with TinkerPop 3.7.3 and Gremlin-Groovy over HTTP, using BerkeleyJE storage in Docker on macOS ARM64. The JVM heap was 1 GiB and the container memory limit was 2 GiB. I used the default optimization strategies.

### How to reproduce

Create the schema and graph below in an empty graph. `g` is the graph's traversal source. The setup commits batches of 250 vertices or edges.

```groovy
def graph = g.getGraph()
graph.tx().rollback()
def m = graph.openManagement()
['uid', 'id', 'gsp_probe_key', 'expected_count'].each { k ->
    if (m.getPropertyKey(k) == null)
        m.makePropertyKey(k)
            .dataType(Long.class)
            .cardinality(org.janusgraph.core.Cardinality.SINGLE)
            .make()
}
if (m.getPropertyKey('mark') == null)
    m.makePropertyKey('mark')
        .dataType(Boolean.class)
        .cardinality(org.janusgraph.core.Cardinality.SINGLE)
        .make()

    m.makePropertyKey('_gsp_identity')
        .dataType(String.class)
        .cardinality(org.janusgraph.core.Cardinality.SINGLE)
        .make()
['ScorRoot', 'ScorTarget'].each { label ->
    if (m.getVertexLabel(label) == null)
        m.makeVertexLabel(label).make()

['GSP_SC_HIGH', 'GSP_SC_REF'].each { label ->
    if (m.getEdgeLabel(label) == null)

            .multiplicity(org.janusgraph.core.Multiplicity.MULTI)
            .make()

if (m.getGraphIndex('gsp_internal_identity') == null)

        .addKey(m.getPropertyKey('_gsp_identity'))
        .unique()

        .addKey(m.getPropertyKey('id'))
        .indexOnly(m.getVertexLabel('ScorRoot'))
        .buildCompositeIndex()
m.commit()
['gsp_internal_identity', 'gsp_cost_lookup_ScorRoot_id'].each { name ->
    org.janusgraph.graphdb.database.management.ManagementSystem
        .awaitGraphIndexStatus(graph, name)
        .status(
            org.janusgraph.core.schema.SchemaStatus.REGISTERED,
            org.janusgraph.core.schema.SchemaStatus.ENABLED

        .timeout(60, java.time.temporal.ChronoUnit.SECONDS)
        .call()
    def mg = graph.openManagement()
    def index = mg.getGraphIndex(name)
    if (index.getFieldKeys().any {
        index.getIndexStatus(it) != org.janusgraph.core.schema.SchemaStatus.ENABLED
    })
        mg.updateIndex(index, org.janusgraph.core.schema.SchemaAction.ENABLE_INDEX)
            .get()
    mg.commit()
}

g.addV('ScorRoot')
    .property('_gsp_identity', 'ScorRoot:1')
    .property('uid', 1L)
    .property('id', 1L)
    .property('gsp_probe_key', 1L)
    .property('expected_count', 40000L)
    .iterate()
graph.tx().commit()
(1..40000).each { i ->
    def uid = 680487L + i
    g.addV('ScorTarget')
        .property('_gsp_identity', 'ScorTarget:' + uid)
        .property('uid', uid)
        .property('mark', true)
        .property('gsp_probe_key', 1L)
        .iterate()
    if (i % 250 == 0) graph.tx().commit()
}
(2L..4L).each { uid ->
    g.addV('ScorTarget')
        .property('_gsp_identity', 'ScorTarget:' + uid)
        .property('uid', uid)
        .property('mark', true)
        .property('gsp_probe_key', 1L)
        .iterate()
}
graph.tx().commit()
(1..40000).each { i ->
    def root = g.V()
        .has('_gsp_identity', 'ScorRoot:1')
        .next()
    def target = g.V()
        .has('_gsp_identity', 'ScorTarget:' + (680487L + i))
        .next()
    root.addEdge('GSP_SC_HIGH', target)
    if (i % 250 == 0) graph.tx().commit()
}
(2L..4L).each { uid ->
    g.V()
        .has('_gsp_identity', 'ScorRoot:1')
        .next()
        .addEdge(
            'GSP_SC_REF',
            g.V()
                .has('_gsp_identity', 'ScorTarget:' + uid)
                .next()
        )
}
graph.tx().commit()
```

There is one indexed `ScorRoot` with `id=1`, followed by 40,000 `GSP_SC_HIGH` neighbors. Every target has `mark=true`, so none passes `mark=false`. Three additional reference edges reproduce the same data state but are not used by either query. Run q1 and q2 above and fully consume each traversal.

For q1, I get an empty result, `[]`. Median runtime: **296.96 ms**.

For q2, I also get `[]`. Median runtime: **1.46 ms**.

I measured 40 paired runs across two independently rebuilt graphs, with three warm-up pairs before each set of 20. Timing includes full result consumption and excludes profiling. The median paired q1/q2 ratio was **201.40×**; the median paired runtime difference was **294.92 ms**. Repeated q1/q1 and q2/q2 controls had a 99th-percentile difference of **21.21 ms**.

`explain()` and `profile()` give these excerpts:

```text
q1 final traversal:
  JanusGraphStep: ScorRoot, id.eq(1)
  TraversalFilterStep: out(GSP_SC_HIGH), mark.eq(false)
  HasStep: id.eq(0)

q1 PROFILE:
  JanusGraphVertexStep(OUT,[GSP_SC_HIGH],vertex): elementCount = 40000
  GSP_SC_HIGH backend-query: elementCount = 40000
  property backend-query: 160000 entries in 16 batches

q2 final traversal:
  JanusGraphStep: ScorRoot, id.eq(1), id.eq(0)
  TraversalFilterStep: out(GSP_SC_HIGH), mark.eq(false)

q2 PROFILE:
  No GSP_SC_HIGH backend-query is executed.
```

`FilterRankingStrategy` runs before `InlineFilterStrategy`. In q1, the last filter becomes a `HasStep` only after ranking, and remains behind the traversal filter. JanusGraph visits all 40,000 neighbors and reads their properties even though `id=0` can reject the root first. In q2, the bare `HasStep` is moved forward and folded into the root conditions before any neighbor is visited.

### Expected performance

Could you apply the same early vertex filtering after q1's wrapped `has()` is inlined, so q1 skips the unnecessary neighbor and property reads as q2 already does?
