# A singleton within predicate misses unique-index adjacency optimization

### Describe the situation

Hi, JanusGraph developers,

For both queries, bind `target_key` to the String `ScorTarget:680488`.

Please consider these two queries:

```groovy
// q1
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .out('GSP_SC_HIGH')
    .has('_gsp_identity', P.within(target_key))
    .project('uid')
    .by(__.values('uid'))

// q2
g.V()
    .hasLabel('ScorRoot')
    .has('id', 1)
    .out('GSP_SC_HIGH')
    .has('_gsp_identity', P.eq(target_key))
    .project('uid')
    .by(__.values('uid'))
```

I use a one-element `within()` predicate in q1 and equality in q2. `_gsp_identity` is a SINGLE String property with a unique composite index, so these predicates match the same vertices and preserve repeated edges. On the graph below, both queries return `uid=680488`, but q1 takes about 177 times as long as q2.

### Which JanusGraph versions are affected?

I tested JanusGraph 1.1.0 with TinkerPop 3.7.3 and Gremlin-Groovy over HTTP, using BerkeleyJE storage in Docker on macOS ARM64. The JVM heap was 1 GiB and the container memory limit was 2 GiB. `query.optimizer-backend-access` was `true`, and `gsp_internal_identity` was an ENABLED unique composite index. I used the default optimization strategies.

There is one indexed root with 40,000 `GSP_SC_HIGH` neighbors. Exactly one target has `_gsp_identity='ScorTarget:680488'`. Three additional reference edges reproduce the same data state but are not used by either query. Bind `target_key` as described above, run q1 and q2 separately, and fully consume each traversal.

For q1, I get one row: `[uid:680488]`. Median runtime: **298.65 ms**.

For q2, I get the same row. Median runtime: **1.69 ms**.

I measured 40 paired runs across two independently rebuilt graphs, with three warm-up pairs before each set of 20. Timing includes full result consumption and excludes profiling. The median paired q1/q2 ratio was **176.70×**; the median paired runtime difference was **297.03 ms**. Repeated q1/q1 and q2/q2 controls had a 99th-percentile difference of **31.86 ms**.

`explain()` and `profile()` give these excerpts. The adjacent vertex ID in q2 is JanusGraph's allocated internal ID for the target in this run:


For q2, `AdjacentVertexHasUniquePropertyOptimizerStrategy` uses the unique property index to resolve the target vertex and pushes its ID into the adjacency query. q1 retains the property filter after the expansion and visits all 40,000 neighbors. The inspected strategy recognizes `Compare.eq`, so the one-element `within()` predicate does not receive the same optimization.

### Expected performance

Could you apply the same unique-index adjacency optimization to a one-element String `within()` predicate, so q1 skips the other neighbors as q2 already does?
