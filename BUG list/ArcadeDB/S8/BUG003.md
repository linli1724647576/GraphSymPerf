# Gremlin materializes all matching neighbors before an existence test

### Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

Use the integer binding `{"_gsp_p0":1}` for both.

```gremlin
// q1
g.inject(1)
    .V()
    .hasLabel('ScorRoot')
    .has('id', P.eq(_gsp_p0))
    .as('_gsp_v0')
    .filter(
        __.select('_gsp_v0')
            .outE('GSP_SC_HIGH')
            .inV()
            .hasLabel('ScorTarget')
            .as('_gsp_v1')
    )
    .project('c0')
    .by(
        __.select('_gsp_v0')
            .coalesce(__.values('uid'), __.constant(null))
    );

// q2
g.inject(1)
    .V()
    .hasLabel('ScorRoot')
    .has('id', P.eq(_gsp_p0))
    .as('_gsp_v0')
    .filter(
        __.select('_gsp_v0')
            .outE('GSP_SC_REF')
            .inV()
            .hasLabel('ScorTarget')
            .as('_gsp_v1')
    )
    .project('c0')
    .by(
        __.select('_gsp_v0')
            .coalesce(__.values('uid'), __.constant(null))
    );
```

Both queries return one row, `{"c0":1}`, on the graph below. They differ only in the relationship type used to find a matching neighbor; the filter needs one match. I observe a median paired q1/q2 runtime ratio of **26.66×**.

### Which ArcadeDB versions are affected?

I tested the ArcadeDB **26.10.2** release distribution, build `e854692736b48971f92dff78a1e727bc570bb6a2` (`1792085686249/main`), with TinkerPop **3.8.2** and the default Java Gremlin engine through native HTTP. The server ran in a Linux/arm64 Docker container on macOS ARM64, with `-Xms1g -Xmx4g`.

### How to reproduce

Start with an empty database. Set `ARCADEDB_PASSWORD`; the Python standard-library script below defaults to user `root`, database `gsp_gremlin` and `http://localhost:2488`. Set `ARCADEDB_USER`, `ARCADEDB_DATABASE` or `ARCADEDB_URL` if needed. It creates the schema, loads all vertices before the edges in batches of 1,000, and then creates the same index used in my measurements.

```python
"""Standard-library, empty-database reproduction of the measured S5/S6/S8 graph."""
import base64
import http.client
import json
import os
from itertools import chain, islice
from urllib.parse import quote, urlsplit

N = 150000
url = urlsplit(os.environ.get("ARCADEDB_URL", "http://localhost:2488"))
database = quote(os.environ.get("ARCADEDB_DATABASE", "gsp_gremlin"), safe="")
token = base64.b64encode((os.environ.get("ARCADEDB_USER", "root") + ":" +
                         os.environ["ARCADEDB_PASSWORD"]).encode()).decode()
connection = (http.client.HTTPSConnection if url.scheme == "https" else
              http.client.HTTPConnection)(url.hostname, url.port, timeout=30)

def request(endpoint, body, ndjson=False):
    data = body.encode() if ndjson else json.dumps(body).encode()
    connection.request("POST", url.path.rstrip("/") + "/api/v1/" + endpoint,
                       data, {"Authorization": "Basic " + token,
                              "Content-Type": "application/x-ndjson" if ndjson else "application/json"})
    response = connection.getresponse()
    result = json.loads(response.read())
    assert response.status == 200 and not result.get("error"), result
    return result

def sql(command, write=False):
    return request(("command/" if write else "query/") + database,
                   {"language": "sql", "command": command})["result"]

assert N > 0 and not sql("SELECT name FROM schema:types"), "Use an empty database"
assert not sql("SELECT typeName FROM schema:indexes"), "Use an empty database"
for name, kind, properties in (
    ("ScorRoot", "VERTEX", {"uid": "LONG", "id": "LONG", "key": "LONG", "expected_count": "LONG"}),
    ("ScorTarget", "VERTEX", {"uid": "LONG", "mark": "BOOLEAN", "key": "LONG"}),
    ("GSP_SC_HIGH", "EDGE", {}), ("GSP_SC_REF", "EDGE", {})):
    sql(f"CREATE {kind} TYPE {name}", True)
    for key, datatype in properties.items():
        sql(f"CREATE PROPERTY {name}.{key} {datatype}", True)

def batches(rows):
    iterator = iter(rows)
    while batch := list(islice(iterator, 1000)):
        yield batch

def target(uid):
    return {"@type": "vertex", "@class": "ScorTarget", "@id": f"ScorTarget:{uid}",
            "uid": uid, "mark": True, "key": 1}

vertices = chain(
    [{"@type": "vertex", "@class": "ScorRoot", "@id": "ScorRoot:1",
      "uid": 1, "id": 1, "key": 1, "expected_count": 4 * N}],
    (target(895440 + i) for i in range(1, 4 * N + 1)),
    (target(i) for i in range(2, 5)))
ids = {}
for batch in batches(vertices):
    result = request("batch/" + database + "?wal=true&lightEdges=false",
                     "".join(json.dumps(row) + "\n" for row in batch), True)
    assert result["verticesCreated"] == len(batch) and result["edgesCreated"] == 0
    assert set(result["idMapping"]) == {row["@id"] for row in batch}
    ids.update(result["idMapping"])

edges = chain(
    (("GSP_SC_HIGH", 895440 + i) for i in range(1, 4 * N + 1)),
    (("GSP_SC_REF", i) for i in range(2, 5)))
records = ({"@type": "edge", "@class": kind, "@from": ids["ScorRoot:1"],
            "@to": ids[f"ScorTarget:{uid}"]} for kind, uid in edges)
for batch in batches(records):
    result = request("batch/" + database + "?wal=true&lightEdges=false",
                     "".join(json.dumps(row) + "\n" for row in batch), True)
    assert result["verticesCreated"] == 0 and result["edgesCreated"] == len(batch)
sql("CREATE INDEX gsp_cost_lookup ON ScorRoot (id) NOTUNIQUE", True)
print(json.dumps({"vertices": len(ids), "edges": 4 * N + 3, "scale": N}))
connection.close()
```

Run q1 and q2 above through `POST /api/v1/query/<database>`, with `language` set to `gremlin`, the query text in `command`, `params` set to `{"_gsp_p0":1}`, `limit` set to `10001` and `serializer` set to `record`.

The indexed root has 600,000 outgoing `GSP_SC_HIGH` relationships and three outgoing `GSP_SC_REF` relationships. Every destination is a `ScorTarget`, so either existence test succeeds on its first matching neighbor.

For q1, I get one row: `{"c0":1}`. Median runtime: **160.21 ms**.

For q2, I get the same row: `{"c0":1}`. Median runtime: **6.02 ms**.

I rebuilt the graph twice and measured 20 balanced AB/BA pairs per rebuild after five warm-up pairs, plus ten A/A and ten B/B control pairs, reading and decoding each full HTTP result without profiling. Across the 40 ordinary paired runs, the median q1/q2 ratio was **26.66×** (95% bootstrap interval **24.79–28.03×**) and the median paired difference was **154.79 ms**; the ratio is the median of paired ratios, not the quotient of the two runtime medians.

In separate requests, setting `profileExecution` to `detailed` produces these native GremlinExecutionPlan excerpts. `cost` and `totalCost` are PROFILE nanoseconds; `totalCost` includes nested steps. They are not the ordinary runtimes above.

```text
q1:
ArcadeFilterByIndexStep(vertex,ScorRoot,gsp_cost_lookup,eq([1]))
  elements=1, traversers=1, cost=94417, totalCost=94417
VertexStep(OUT,[GSP_SC_HIGH],vertex)
  elements=1, traversers=1, cost=230370209, totalCost=230370209
q2:
ArcadeFilterByIndexStep(vertex,ScorRoot,gsp_cost_lookup,eq([1]))
  elements=1, traversers=1, cost=40792, totalCost=40792
VertexStep(OUT,[GSP_SC_REF],vertex)
  elements=1, traversers=1, cost=6785417, totalCost=6785417
```

The plans use the same root index and each `VertexStep` emits only one vertex. However, [`ArcadeVertex.vertices()`](https://github.com/ArcadeData/arcadedb/blob/e854692736b48971f92dff78a1e727bc570bb6a2/gremlin/src/main/java/com/arcadedb/gremlin/ArcadeVertex.java#L284-L302) fills an `ArrayList` before returning its iterator; [`VertexStep`](https://github.com/apache/tinkerpop/blob/3.8.2/gremlin-core/src/main/java/org/apache/tinkerpop/gremlin/process/traversal/step/map/VertexStep.java#L71-L75) calls this method before it can yield the first neighbor. Thus the checked graph and source imply that q1 wraps 600,000 matching neighbors before the existence filter can stop, while q2 wraps three; these are source-derived internal counts, not PROFILE allocation or physical-I/O counters.

### Expected performance

Could you return matching neighbors lazily, preserving their order, duplicates and visibility, so the existence test can stop before the unused neighbors are looked up and wrapped, avoiding the bulk of that work as q2 does here?
