> Current-version review (2026-10-31): **follow_up**. Submission target: Memgraph. ### Describe the situation

Hi, Memgraph developers,

Please consider these two queries:

```cypher
// q1
MATCH (a:GspLow)
WHERE (a.id = 1)
MATCH (b:GspHigh)-[:GSP_LINK]->(c:GspTarget)
WHERE (c.keep = true)
RETURN a.uid, b.uid, c.uid;

// q2
MATCH (b:GspHigh)-[:GSP_LINK]->(c:GspTarget)
WHERE (c.keep = true)
MATCH (a:GspLow)
WHERE (a.id = 1)
RETURN a.uid, b.uid, c.uid;
```

I swap two independent `MATCH` clauses and get no rows from either query, because no `GspLow` node has `id=1`. In q1, Memgraph stops after the empty index lookup. In q2, it scans the large branch before checking the same index, and I measure about 166 times the runtime of q1.

### Which Memgraph versions are affected?

I ran this case on Memgraph 3.10.1 with Cypher, using the Memgraph Docker image on macOS ARM64. I ran `ANALYZE GRAPH` after loading each fresh graph and before measuring the queries.

### How to reproduce

Create this graph in an empty database, then run q1 and q2 above:

```cypher
CREATE INDEX ON :GspLow(id);

CREATE (:GspLow {uid: 1, id: 0}),
       (:GspHigh {uid: 2})-[:GSP_LINK]->(:GspTarget {uid: 3, keep: true});

UNWIND range(1, 200000) AS i
CREATE (b:GspHigh {uid: 895440+5*i})
WITH b, i
UNWIND range(1, 4) AS j
CREATE (b)-[:GSP_LINK]->(:GspTarget {uid: 895440+5*i+j, keep: false});

ANALYZE GRAPH;
```

The only `GspLow` node has `id=0`. The independent high branch has 800,001 links, of which only the link to target 3 passes `c.keep=true`. None can contribute to the final result without a match for `a.id=1`.

For q1, I get no rows. Median runtime: **0.79 ms**.

For q2, I get no rows. Median runtime: **135.68 ms**.

I measured 40 paired runs across two fresh graph loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `PROFILE`; the median paired q2/q1 runtime ratio was **165.54×**, and the median paired runtime difference was **134.75 ms**.

Adding `PROFILE` gives these excerpts from the native `ACTUAL HITS` fields:

```text
q1:
Operator                                      ACTUAL HITS
Produce {a.uid, b.uid, c.uid}                            1
Cartesian                                              1
ScanAllByLabelProperties (a :GspLow {id})                1

q2:
Operator                                      ACTUAL HITS
Produce {a.uid, b.uid, c.uid}                            1
Cartesian                                              1
  ScanAllByLabelProperties (a :GspLow {id})              1
  Filter (c :GspTarget), {c.keep}                        2
    Expand (b)-[anon1:GSP_LINK]->(c)                800002
      Filter (b :GspHigh)                          200002
        ScanAll (b)                              1000004
```

For q2, Memgraph scans the graph, expands all 800,001 high links and checks their targets before the Cartesian operator reads the empty index result. For q1, it reads that empty result first and executes none of the high-branch scan or expansion operators.

### Expected performance

Could Memgraph check the small indexed input first in q2, as q1 does, so the Cartesian product can stop without scanning the independent high branch when the lookup returns no rows?
