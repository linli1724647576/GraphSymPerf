# Repeated expansion after swapping two MATCH clauses

## Describe the situation

Hi, Memgraph developers,

Please consider these two queries:

```cypher
// q1
MATCH (u:GspAnchor {uid: 1})
MATCH (u)-[:GSP_HIGH]->(w:GspHigh)
WHERE (NOT (w.keep = false))
MATCH (u)-[:GSP_LOW]->(v:GspLow)
RETURN u.uid, v.uid, w.uid;

// q2
MATCH (u:GspAnchor {uid: 1})
MATCH (u)-[:GSP_LOW]->(v:GspLow)
MATCH (u)-[:GSP_HIGH]->(w:GspHigh)
WHERE (NOT (w.keep = false))
RETURN u.uid, v.uid, w.uid;
```

I swap two `MATCH` clauses that share `u`, keeping the relationships, condition and output unchanged. Both queries return the same eight rows on the graph below. In q2, Memgraph repeats the expansion through `GSP_HIGH` for each match of `v`, and I measure about 5.5 times the runtime of q1.

## Which Memgraph versions are affected?

I ran this case on Memgraph 3.10.1 with Cypher, using the Memgraph Docker image on macOS ARM64. I ran `ANALYZE GRAPH` after loading each fresh graph and before measuring the queries.

## How to reproduce

Create this graph in an empty database, then run q1 and q2 above:

```cypher
CREATE INDEX ON :GspAnchor(uid);

CREATE (u:GspAnchor {uid: 1})-[:GSP_LOW]->(:GspLow {uid: 2})
CREATE (u)-[:GSP_HIGH]->(:GspHigh {uid: 3, keep: true});

MATCH (u:GspAnchor {uid: 1})
UNWIND range(1, 200000) AS i
CREATE (u)-[:GSP_HIGH]->(:GspHigh {uid: 895440+i, keep: false});

MATCH (u:GspAnchor {uid: 1})
UNWIND range(1, 7) AS i
CREATE (u)-[:GSP_LOW]->(:GspLow {uid: -i});

ANALYZE GRAPH;
```

Node `u` has eight `GSP_LOW` neighbors and 200,001 `GSP_HIGH` neighbors. Only the high neighbor with `uid=3` has `keep=true`; the other 200,000 neighbors cannot pass the condition.

For q1, I get eight rows in columns `(u.uid, v.uid, w.uid)`: `(1, 2, 3)`, `(1, -1, 3)`, `(1, -2, 3)`, `(1, -3, 3)`, `(1, -4, 3)`, `(1, -5, 3)`, `(1, -6, 3)` and `(1, -7, 3)`. Median runtime: **32.44 ms**.

For q2, I get the same eight rows. Median runtime: **178.81 ms**.

I measured 40 paired runs across two fresh graph loads, with five warm-up pairs per load and both q1/q2 and q2/q1 execution orders. I read the full result without `PROFILE`; the median paired q2/q1 runtime ratio was **5.53×**, and the median paired runtime difference was **145.67 ms**.

Adding `PROFILE` gives these excerpts from the native `ACTUAL HITS` fields:

```text
q1:
Operator                                      ACTUAL HITS
Produce {u.uid, v.uid, w.uid}                            9
Filter (v :GspLow)                                      9
Expand (u)-[anon4:GSP_LOW]->(v)                          9
Filter (u :GspAnchor), {u.uid}                           2
Expand (w)<-[anon2:GSP_HIGH]-(u)                         2
Filter (w :GspHigh), Generic {w}                         2
ScanAll (w)                                       200011

q2:
Operator                                      ACTUAL HITS
Produce {u.uid, v.uid, w.uid}                            9
Filter (w :GspHigh), Generic {w}                         9
Expand (u)-[anon4:GSP_HIGH]->(w)                   1600009
Filter (u :GspAnchor), {u.uid}                           9
Expand (v)<-[anon2:GSP_LOW]-(u)                          9
Filter (v :GspLow)                                      9
ScanAll (v)                                       200011
```

For q2, Memgraph starts from the low neighbors and reaches the same `u` eight times. It then traverses the 200,001 high edges and checks `keep` for each low-neighbor match. For q1, Memgraph scans for the high neighbor that passes `keep`, follows its edge back to `u` once, and then expands the eight low edges.

## Expected performance

Could Memgraph choose an order for q2 that checks `w.keep` before multiplying the matches of `u`, as q1 does, so it avoids repeating the same high-edge traversal?
