# Performance difference between two undirected path queries

## Describe the situation

Hi, Neo4j developers,

Please consider these two queries:

```cypher
// q1
MATCH p = (u:GspLow {id: 1})-[:GSP_LINK*1..3]-(v:GspHigh)
WHERE all(x IN nodes(p) WHERE (x.keep = true))
RETURN u.uid, v.uid, length(p) AS hops;

// q2
MATCH p = (v:GspHigh)-[:GSP_LINK*1..3]-(u:GspLow {id: 1})
WHERE all(x IN nodes(p) WHERE (x.keep = true))
RETURN u.uid, v.uid, length(p) AS hops;
```

Both queries match the same undirected paths and check that each node has `keep=true`. I write the path in reverse order in q2. On the graph below, I get the same result from both queries, but q2 takes about 200 times as long as q1.

## Which Neo4j versions are affected?

I ran this case on Neo4j 2026.09.0 Community with Cypher 25, in Docker on macOS ARM64. The container has 4 CPUs and 6 GiB of memory, with a 4 GiB heap and a 512 MiB page cache. Both plans use the COST planner and SLOTTED runtime.

## How to reproduce

Create this graph in an empty database, then run q1 and q2 above:

```cypher
CREATE INDEX gsp_cost_lookup IF NOT EXISTS
FOR (n:GspLow) ON (n.id);

CREATE (u:GspLow {uid: 1, id: 1, keep: true})
       -[:GSP_LINK]->(:GspMiddle {uid: 2, keep: true})
       -[:GSP_LINK]->(:GspHigh {uid: 3, keep: true})
CREATE (u)-[:GSP_LINK]->(:GspBad {uid: 0, keep: false});

MATCH (b:GspBad {uid: 0})
UNWIND range(1, 300000) AS i
CREATE (b)-[:GSP_LINK]->
       (:GspMiddle {uid: 895440 + 2*i, keep: true})
       -[:GSP_LINK]->
       (:GspHigh {uid: 895440 + 2*i + 1, keep: true});

CALL db.awaitIndexes(120);
CALL db.prepareForReplanning();
```

The node `GspBad` has `keep=false`, with 300,000 two-hop branches behind it. Those branches cannot match either query. A separate two-hop path from `u` to node 3 has `keep=true` on each node. The graph has 600,004 nodes and 600,003 relationships.

For q1, I get one row: `(u.uid, v.uid, hops) = (1, 3, 2)`. Median runtime: **2.70 ms**.

For q2, I get the same row. Median runtime: **530.10 ms**.

I measured 20 paired runs on each of two separately rebuilt graphs, after 10 warm-up pairs per graph, with balanced AB/BA order. The timings include full result consumption and the client/Bolt round trip, without `PROFILE`; all 40 pairs returned the same row. The median q2/q1 runtime ratio across the 40 paired runs was **199.66×**, with per-graph medians of **199.50×** and **200.01×**.

Adding `PROFILE` to q1 and q2 gives these plan excerpts:

```text
q1:
Operator               Rows   DB Hits   Relevant detail
Filter                    1         2   v:GspHigh
VarLengthExpand(All)      2        12   WHERE all(x IN nodes(p) WHERE x.keep = true)
NodeIndexSeek             1         2   u:GspLow(id)
Total DB Hits: 18

q2:
Operator               Rows   DB Hits   Relevant detail
Filter                    1   1500006   v:GspHigh AND all(x IN nodes((v)-[anon_0*]-(u)) ...)
VarLengthExpand(All) 600003   1200010   (u)-[anon_0:GSP_LINK*..3]-(v)
NodeIndexSeek             1         2   u:GspLow(id)
Total DB Hits: 2700020
```

Neo4j starts both queries from the indexed node `u`. For q1, it checks `keep` during traversal and stops at `GspBad`. For q2, it visits the nodes behind `GspBad` before checking the same condition. The expansion produces 600,003 rows instead of 2, with 2,700,020 total DB Hits instead of 18.

## Expected performance

Could Neo4j check the node condition during traversal in q2 as it does in q1, so that both queries skip the branch through `GspBad`?
