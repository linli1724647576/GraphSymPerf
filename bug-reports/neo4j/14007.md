# Unnecessary traversal with AND and EXISTS

## Describe the situation

Hi, Neo4j developers,

Please consider these two queries:

```cypher
// q1
MATCH (u:GspAnchor)
WHERE ((((coalesce(u.keep, false) = true) AND (u.uid = u.uid))
  OR (NOT (u.uid = u.uid))) AND EXISTS {
    MATCH (u)-[:GSP_EXPAND]->(gsp_leaf:GspLeaf)
    WHERE (((gsp_leaf.mark = true) AND (u.uid = u.uid))
      OR (NOT (u.uid = u.uid)))
  })
RETURN u.uid;

// q2
MATCH (u:GspAnchor)
WHERE CASE
  WHEN ((((coalesce(u.keep, false) = true) AND (u.uid = u.uid))
    OR (NOT (u.uid = u.uid))) = false) THEN false
  ELSE ((((coalesce(u.keep, false) = true) AND (u.uid = u.uid))
    OR (NOT (u.uid = u.uid))) AND EXISTS {
      MATCH (u)-[:GSP_EXPAND]->(gsp_leaf:GspLeaf)
      WHERE (((gsp_leaf.mark = true) AND (u.uid = u.uid))
        OR (NOT (u.uid = u.uid)))
    })
END
RETURN u.uid;
```

In q1, I combine a node condition with an `EXISTS` subquery using `AND`. In q2, I use `CASE` to return false when the node condition is false. Both queries return the same result, but Neo4j runs the subquery for the node with `keep=false` in q1. On the graph below, q1 takes about 86 times as long as q2.

## Which Neo4j versions are affected?

I ran this case on Neo4j 2026.09.0 Community with Cypher 25, in Docker on macOS ARM64. Both plans use the COST planner and SLOTTED runtime.

## How to reproduce

Create this graph in an empty database, then run q1 and q2 above:

```cypher
CREATE INDEX gsp_cost_lookup IF NOT EXISTS
FOR (n:GspAnchor) ON (n.uid);

CREATE (:GspAnchor {uid: 1, keep: false});
CREATE (:GspAnchor {uid: 2, keep: true})
       -[:GSP_EXPAND]->(:GspLeaf {uid: 3, mark: true});

MATCH (u:GspAnchor {uid: 1})
UNWIND range(1, 400000) AS i
CREATE (u)-[:GSP_EXPAND]->
       (:GspLeaf {uid: 895440 + i, mark: false});

CALL db.awaitIndexes(60);
CALL db.prepareForReplanning();
```

Node 1 has `keep=false` and 400,000 outgoing relationships. None of its leaves has `mark=true`. Node 2 has `keep=true` and one leaf with `mark=true`.

For q1, I get one row: `u.uid = 2`. Median runtime: **169.52 ms**.

For q2, I get the same row. Median runtime: **2.02 ms**.

I measured 40 runs of each query after warm-up and read the full result without `PROFILE`. The median q1/q2 runtime ratio across the 40 paired runs was **86.38×**.

Adding `PROFILE` to q1 and q2 gives these plan excerpts:

```text
q1:
Operator        Rows     DB Hits   Relevant detail
Filter             1           1   keep condition
SemiApply          1           0
  Expand(All) 400001      400004   (u)-[:GSP_EXPAND]->(gsp_leaf)
  Filter           0      400002   gsp_leaf.mark condition
Total DB Hits: 800013

q2:
Operator           Rows   DB Hits   Relevant detail
Filter                1        17   CASE condition with EXISTS
NodeByLabelScan       2         3   u:GspAnchor
Total DB Hits: 20
```

For q1, Neo4j checks the `EXISTS` subquery before the outer `keep` condition. It visits all 400,000 leaves of node 1, even though `keep=false` means that node cannot pass the `WHERE` condition. With the CASE form, Neo4j skips those leaves. Total DB Hits drop from 800,013 to 20.

## Expected performance

Could Neo4j check the node condition before running the `EXISTS` subquery in q1, so that it skips the leaves of node 1 as it does in q2?
