# An edge check against a bound match() vertex fetches the whole adjacency list

## Describe the situation

Hi, JanusGraph developers,

Please consider these two queries. Bind `p0` to the integer `1` for both.

```groovy
// q1
g.V().hasLabel("Random_label_2").has("p_anchor",p0)
 .match(
   __.as("p_match_u").out("Pattern_p_left_edge").hasLabel("Pattern_p_match_label_0").as("p_match_0"),
   __.as("p_match_u").where(__.out("Pattern_p_right_edge").as("p_match_0")))
 .select("p_match_u").as("v1").select("v1").constant(2.5d)

// q2
g.V().hasLabel("Random_label_2").has("p_anchor",p0)
 .match(
   __.as("p_match_u").out("Pattern_p_left_edge").hasLabel("Pattern_p_match_label_0").as("p_match_0"),
   __.as("p_match_0").where(__.in("Pattern_p_right_edge").as("p_match_u")))
 .select("p_match_u").as("v1").select("v1").constant(2.5d)
```

Both queries ask whether a `Pattern_p_right_edge` edge connects the two vertices already bound to `p_match_u` and `p_match_0`. q1 checks it from `p_match_u`, q2 from `p_match_0`. They return the same single row. `p_match_u` has 100,001 outgoing `Pattern_p_right_edge` edges, and q1 fetches all of them from the backend although the traversal stops after 18. q1 takes about 55 times as long as q2.

## Which JanusGraph versions are affected?

I tested JanusGraph 1.2.0 (TinkerPop 3.8.2, Java 11) with BerkeleyJE storage, the `janusgraph/janusgraph:1.2.0` Docker image on macOS ARM64, 2 CPUs and 3 GiB memory, GraphSON 3 over the Gremlin HTTP endpoint, `schema.default=none`, `query.force-index=false`, and default strategies.

The setup creates 100,051 vertices and 100,102 edges. Run q1 and q2 above on this graph.

The relevant part of the data:

- One `Random_label_2` vertex `u` has `p_anchor = 1`. It has one `Pattern_p_left_edge` edge to a `Pattern_p_match_label_0` vertex `t`.
- `u` has 100,001 outgoing `Pattern_p_right_edge` edges: one to `t` and 100,000 to `Pattern_p_match_label_1` vertices.
- `t` has a single incoming `Pattern_p_right_edge` edge, the one from `u`.

For q1, I get one row: `2.5`. Median runtime: 107.482 ms.

For q2, I get one row: `2.5`. Median runtime: 1.960 ms.

Each runtime is the median of 20 runs per query, alternating q1/q2 and q2/q1 order, after 5 warm-up pairs, with the full result read. q1 is the slower query; the median paired q1/q2 ratio is about 55x. `PROFILE` ran after the timed runs.

PROFILE excerpt for q1:

```text

  JanusGraphVertexStep(OUT,[Pattern_p_right_edge],vertex)   traversers=18  elements=18
    backend-query                                             elements=100001
```

PROFILE excerpt for q2:

```text
WhereTraversalStep([WhereStartStep(null), JanusGraphMultiQueryStep, JanusGraphNoOpBarrierVertexOnlyStep(2500), JanusGraphVertexStep(IN,[Pattern_p_right_edge],vertex), WhereEndStep(p_match_u)])
  JanusGraphVertexStep(IN,[Pattern_p_right_edge],vertex)    traversers=1   elements=1
    backend-query                                             elements=1
```

In q1, the `backend-query` under `JanusGraphVertexStep(OUT,...)` reads all 100,001 relations of `u` for that edge label. `WhereEndStep(p_match_0)` then compares the adjacent vertices with `t` in memory and stops at the 18th. In q2 the same check starts at `t`, which has one such relation. Both endpoints are known when the `where()` runs. JanusGraph stores relations with the adjacent vertex id in the column, and `AdjacentVertexFilterOptimizerStrategy` already uses that for `out(label).is(v)` with a constant vertex, so the check could read only the relations to `t`.

## Expected performance

When the end of `where(out(label).as(x))` or `where(in(label).as(x))` is compared with an already bound vertex, I would like JanusGraph to add that vertex as an adjacent-vertex constraint on the edge query, the way `AdjacentVertexFilterOptimizerStrategy` handles `out(label).is(v)`, instead of fetching the full adjacency list as q1 does.
