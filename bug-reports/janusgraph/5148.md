# LIMIT(1) still preloads the complete adjacency list

## Describe the situation

Hi, JanusGraph developers,

Please consider these two queries:

```groovy
// q1
(g.inject(1).V().hasLabel('ScorRoot').has('id',P.eq(_gsp_p0)).as('_gsp_v0').outE('GSP_SC_HIGH').inV().hasLabel('ScorTarget').as('_gsp_v1').project('c0').by(__.constant(_gsp_p1)).limit(1)).limit(10001).toList()
```

```groovy
// q2
(g.inject(1).V().hasLabel('ScorRoot').has('id',P.eq(_gsp_p0)).as('_gsp_v0').outE('GSP_SC_REF').inV().hasLabel('ScorTarget').as('_gsp_v1').project('c0').by(__.constant(_gsp_p1)).limit(1)).limit(10001).toList()
```

Send both queries through the Gremlin HTTP endpoint with these integer bindings:

```json
{"_gsp_p0":1,"_gsp_p1":1}
```

The two traversals differ only in the outgoing edge label. Every neighbor in this graph has label `ScorTarget`, so both return one row containing `1`. Although both traversals end in `limit(1)`, the median paired q1/q2 runtime ratio is about 184.04.

## Which JanusGraph versions are affected?

I tested JanusGraph 1.1.0 with TinkerPop 3.7.3 and Gremlin-Groovy over HTTP, using BerkeleyJE storage in Docker on macOS ARM64. The JVM heap was 4 GiB, with the default optimization strategies. The server used `WsAndHttpChannelizer` and a 30,000 ms evaluation timeout. I also checked the queries and plans on newly created storage using the same pinned image, `janusgraph/janusgraph@sha256:75f57aff4b152ca86b4cdaeefb5335154d7fad412cffef75fa44c7504adc96d4`.

## How to reproduce

Start with an empty JanusGraph graph and fresh schema. Run the following Gremlin-Groovy commands in the Gremlin Console with the traversal source bound to `g`.

```groovy
def graph = g.getGraph()
graph.tx().rollback()
def m = graph.openManagement()
['uid', 'id', '_gsp_property_key', 'expected_count'].each {
    m.makePropertyKey(it).dataType(Long.class)
        .cardinality(org.janusgraph.core.Cardinality.SINGLE).make()
}
['mark'].each {
    m.makePropertyKey(it).dataType(Boolean.class)
        .cardinality(org.janusgraph.core.Cardinality.SINGLE).make()
}
['_gsp_identity'].each {
    m.makePropertyKey(it).dataType(String.class)
        .cardinality(org.janusgraph.core.Cardinality.SINGLE).make()
}
['ScorRoot', 'ScorTarget'].each { m.makeVertexLabel(it).make() }
['GSP_SC_HIGH', 'GSP_SC_REF'].each {
    m.makeEdgeLabel(it).multiplicity(org.janusgraph.core.Multiplicity.MULTI).make()
}
m.buildIndex('gsp_internal_identity', org.apache.tinkerpop.gremlin.structure.Vertex.class)
    .addKey(m.getPropertyKey('_gsp_identity')).unique().buildCompositeIndex()
m.buildIndex('gsp_cost_lookup_ScorRoot_id', org.apache.tinkerpop.gremlin.structure.Vertex.class)
    .addKey(m.getPropertyKey('id')).indexOnly(m.getVertexLabel('ScorRoot')).buildCompositeIndex()
m.commit()

g.addV('ScorRoot').property('uid', 1L).property('id', 1L)
    .property('_gsp_property_key', 1L).property('expected_count', 400000L)
    .property('_gsp_identity', 'ScorRoot:1').iterate()
graph.tx().commit()

for (long first = 1L; first <= 400000L; first += 250L) {
    def root = g.V().has('_gsp_identity', 'ScorRoot:1').next()
    for (long i = first; i < first + 250L; i++) {
        long uid = 895440L + i
        def target = graph.addVertex(T.label, 'ScorTarget', 'uid', uid, 'mark', true,
            '_gsp_property_key', 1L, '_gsp_identity', 'ScorTarget:' + uid)
        root.addEdge('GSP_SC_HIGH', target)
    }
    graph.tx().commit()
}

def root = g.V().has('_gsp_identity', 'ScorRoot:1').next()
(2L..4L).each { uid ->
    def target = g.addV('ScorTarget').property('uid', uid).property('mark', true)
        .property('_gsp_property_key', 1L).property('_gsp_identity', 'ScorTarget:' + uid).next()
    root.addEdge('GSP_SC_REF', target)
}
graph.tx().commit()
```

Run q1 and q2 above with the stated bindings.

The root with `id=1` has 400,000 `GSP_SC_HIGH` neighbors and three `GSP_SC_REF` neighbors. All of them have label `ScorTarget`, and there is no additional target predicate. The graph has 400,004 vertices and 400,003 edges.

For q1, I get one row: `[{"c0": 1}]`. **Median runtime: 255.40 ms.**

For q2, I get one row: `[{"c0": 1}]`. **Median runtime: 1.37 ms.**

I measured ordinary queries after two independent graph rebuilds, with five warm-up pairs followed by 20 measured pairs in each session; each session balanced AB/BA order and included ten A/A and ten B/B control pairs. I read the complete results and excluded setup and PROFILE from these times; across the 40 measured pairs, the median q1/q2 ratio was **184.04** and the median paired difference was **254.46 ms** (the ratio is the median of paired ratios).

Both root lookups use `gsp_cost_lookup_ScorRoot_id`. In each traversal, `JanusGraphVertexStep` produces only two traversers before `RangeGlobalStep(0,1)` returns one. However, the provider's backend query has already returned an adjacency collection of 400,000 entries for q1, versus three for q2. The `multi=true, vertices=1` path preloads this collection before the downstream range can stop consumption. Here, `elementCount` counts adjacency entries returned by the backend query.

## Expected performance

Please make adjacency retrieval incremental for this read-only traversal, so `limit(1)` can stop fetching once a matching `ScorTarget` result has been produced.
