# Swapping independent OPTIONAL MATCH clauses repeats the same bound-root lookup

## Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

```cypher
// q1
MATCH (r:GspRoot {uid:0})
OPTIONAL MATCH (r)-[:GSP_LOW]->(l:GspLow)
OPTIONAL MATCH (r)-[:GSP_HIGH]->(h:GspHigh)
RETURN count(h) AS answer

// q2
MATCH (r:GspRoot {uid:0})
OPTIONAL MATCH (r)-[:GSP_HIGH]->(h:GspHigh)
OPTIONAL MATCH (r)-[:GSP_LOW]->(l:GspLow)
RETURN count(h) AS answer
```

I swap two `OPTIONAL MATCH` clauses that share only the already-bound `r`. The low branch has two matches and the high branch has 10,000. Both queries return `answer = 20000`, including the multiplicity contributed by the low branch, but q2 takes about 107.4 times as long.

## Which ArcadeDB versions are affected?

I tested ArcadeDB 26.10.2, build `e854692736b48971f92dff78a1e727bc570bb6a2`, through native HTTP Cypher in Docker on macOS ARM64. The container had 2 CPUs and 3 GiB of memory; the JVM used `-Xms256m -Xmx1024m`. The plans shown below use the traditional execution path.

## How to reproduce

In an empty database, run these schema statements as SQL:

```sql
CREATE VERTEX TYPE GspRoot;
CREATE PROPERTY GspRoot.uid LONG;
CREATE INDEX ON GspRoot (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspLow;
CREATE PROPERTY GspLow.uid LONG;
CREATE PROPERTY GspLow.keep BOOLEAN;
CREATE INDEX ON GspLow (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspHigh;
CREATE PROPERTY GspHigh.uid LONG;
CREATE PROPERTY GspHigh.keep BOOLEAN;
CREATE INDEX ON GspHigh (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspWitness;
CREATE PROPERTY GspWitness.uid LONG;
CREATE PROPERTY GspWitness.keep BOOLEAN;
CREATE INDEX ON GspWitness (uid) NOTUNIQUE;
CREATE EDGE TYPE GSP_LOW;
CREATE EDGE TYPE GSP_HIGH;
CREATE EDGE TYPE GSP_WITNESS;
```

Then run these Cypher statements to create the graph:

```cypher
CREATE (:GspRoot {uid:0});

UNWIND range(1,2) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_LOW]->(:GspLow {uid:i,keep:true});

UNWIND range(3,5) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_WITNESS]->(:GspWitness {uid:i,keep:true});

UNWIND range(6,10005) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_HIGH]->(:GspHigh {uid:i,keep:true});
```

Run q1 and q2 above on this same graph. It has one root, two low leaves, three witness leaves and 10,000 high leaves. All leaves have `keep=true`; each vertex type has the shown `uid` index.

For q1, I get one row: `answer = 20000`. Median runtime: **7.31 ms**.

For q2, I get the same result. Median runtime: **784.53 ms**.

I ran two independently rebuilt sessions. Each used 3 warmup pairs and 6 screening pairs, followed by 5 warmup pairs and 20 alternating AB/BA confirmation pairs; the medians above are from the second confirmation and include complete result consumption. Both sessions exceeded 5x and 100 ms, with the same slower side in every confirmation pair.

The q2/q1 ratio of timing medians is **107.36x**; the median signed paired difference is **773.96 ms**. PROFILE was collected separately after timing.

Native PROFILE excerpts from that rebuilt graph:

```text
q1:
Execution Time: 13.010 ms
Rows Returned: 1
+ MATCH NODE (r:GspRoot) [index: GspRoot[uid]] (8μs, 1 rows)
+ OPTIONAL MATCH (variables: l) (0μs, 2 rows)
    + MATCH NODE (r) (4μs, 1 rows)
+ OPTIONAL MATCH (variables: h) (714μs, 20,000 rows)
    + MATCH NODE (r) (2μs, 2 rows)
+ AGGREGATION count(h) (1,601μs, 20,000 rows)
+ FINAL PROJECTION [answer] (33μs, 1 rows)

q2:
Execution Time: 999.674 ms
Rows Returned: 1
+ MATCH NODE (r:GspRoot) [index: GspRoot[uid]] (6μs, 1 rows)
+ OPTIONAL MATCH (variables: h) (319μs, 10,000 rows)
    + MATCH NODE (r) (1μs, 1 rows)
+ OPTIONAL MATCH (variables: l) (1,526μs, 20,000 rows)
    + MATCH NODE (r) (2,304μs, 10,000 rows)
+ AGGREGATION count(h) (3,797μs, 20,000 rows)
+ FINAL PROJECTION [answer] (28μs, 1 rows)

```

Both plans start with the same indexed root and process 20,000 combined rows before aggregation. In q1, the inner root step under the high optional branch reports two records; in q2, the inner root step under the low optional branch reports 10,000 records. [OptionalMatchStep](https://github.com/ArcadeData/arcadedb/blob/e854692736b48971f92dff78a1e727bc570bb6a2/engine/src/main/java/com/arcadedb/query/opencypher/executor/steps/OptionalMatchStep.java#L225-L241) feeds each input row into the match chain, even though this branch depends on the same `r` in every row. The query returns one aggregate row.

## Expected performance

Could you avoid repeating the identical optional lookup for each duplicate bound root, for example by planning these independent branches in the lower-cost order already used by q1?
