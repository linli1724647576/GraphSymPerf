# COALESCE evaluates a COUNT after a non-null constant

## Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

```cypher
// q1
MATCH (u:ScorRoot {id: 1}) RETURN coalesce(null, 0, COUNT { MATCH (u)-[:GSP_SC_HIGH]->(v:ScorTarget) WHERE (v.mark = true) }) AS c0;

// q2
MATCH (u:ScorRoot {id: 1}) RETURN 0 AS c0;
```

Both queries return `c0 = 0`. In q1, the second `coalesce` argument is the non-null constant `0`, so the final `COUNT` cannot affect the returned value. I still observe over 800,000 record lookups in q1 and about a 218-fold q1/q2 runtime difference.

## Which ArcadeDB versions are affected?

I tested ArcadeDB **26.10.1-SNAPSHOT**, build `ebdf527641ba444364bb9e29aa020e9e04824862` (`1788464335463/main`), a development snapshot. I ran openCypher through the HTTP query interface in Docker on macOS ARM64. The native PROFILE identifies the cost-based optimizer; the property index below is an `LSM_TREE` index.

## How to reproduce

Start with an empty database. Create the schema using SQL:

```sql
CREATE VERTEX TYPE ScorRoot;
CREATE PROPERTY ScorRoot.uid LONG;
CREATE PROPERTY ScorRoot.id LONG;
CREATE PROPERTY ScorRoot.key LONG;
CREATE PROPERTY ScorRoot.expected_count LONG;
CREATE VERTEX TYPE ScorTarget;
CREATE PROPERTY ScorTarget.uid LONG;
CREATE PROPERTY ScorTarget.mark BOOLEAN;
CREATE PROPERTY ScorTarget.key LONG;
CREATE EDGE TYPE GSP_SC_HIGH;
CREATE EDGE TYPE GSP_SC_REF;
```

Load the following data using openCypher:

```cypher
CREATE (:ScorRoot {id: 1, uid: 1, key: 1, expected_count: 400000});

MATCH (u:ScorRoot {id: 1}) UNWIND range(1, 400000) AS i CREATE (u)-[:GSP_SC_HIGH]->(:ScorTarget {uid: 895440+i, mark: true, key: 1});

MATCH (u:ScorRoot {id: 1}) UNWIND range(2, 4) AS i CREATE (u)-[:GSP_SC_REF]->(:ScorTarget {uid: i, mark: true, key: 1});
```

Create the property index using SQL, then run q1 and q2 above:

```sql
CREATE INDEX gsp_cost_lookup ON ScorRoot (id) NOTUNIQUE;
```

The indexed node `ScorRoot {id: 1}` has 400,000 outgoing `GSP_SC_HIGH` relationships to nodes with `mark=true`. The three additional nodes and `GSP_SC_REF` relationships remain in the measured database. The COUNT can find 400,000 matches, but `coalesce(null, 0, ...)` returns the earlier non-null argument `0`.

For q1, I get one row: `c0 = 0`. Median runtime: **219.82 ms**.

For q2, I get the same row. Median runtime: **0.98 ms**.

I rebuilt this graph twice and measured 20 paired runs per rebuild, with five warm-up pairs before each set. I read the full results and included HTTP response transfer and decoding in the runtime; I did not use `PROFILE` for these timings. Across the 40 paired runs, the median q1/q2 ratio was **218.08×** and the median paired time difference was **219.12 ms**.

Adding `PROFILE` gives the following excerpts. `Rows Returned` is the actual result count; `Estimated Rows` is a planning estimate.

```text

Execution Time: 242.023 ms
Rows Returned: 1
Physical operators: Filter [predicate=u.id = 1]
                    NodeIndexSeek(u:ScorRoot) [index=gsp_cost_lookup, id=1]
Estimated Cost: 5.00
Estimated Rows: 0
ProjectReturnStep: 241,817 microseconds, 1 row

q2:
Execution Time: 0.404 ms
Rows Returned: 1
Physical operators: Filter [predicate=u.id = 1]
                    NodeIndexSeek(u:ScorRoot) [index=gsp_cost_lookup, id=1]
Estimated Cost: 5.00
Estimated Rows: 0
ProjectReturnStep: 1 microsecond, 1 row
```

ArcadeDB uses the same indexed lookup for both queries. Most of q1's PROFILE time occurs in `ProjectReturnStep`, where ArcadeDB evaluates every function argument before choosing the first non-null value. The native profiler records 800,402 record lookups for q1 and 1 for q2 in each of two runs, which confirms work inside the projection that the outer operator list does not expose. I obtained these lookup counts from separate, single-query `profiler start`/`profiler stop` windows. ArcadeDB's `readRecord` counter includes cached record lookups; it does not count edge visits or Neo4j DB Hits.

## Expected performance

Could you stop evaluating `coalesce` arguments after finding `0`, or fold this expression to `0`, so that q1 skips the COUNT work that q2 avoids?
