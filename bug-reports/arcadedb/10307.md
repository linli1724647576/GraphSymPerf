# Gremlin scans neighbors before an always-empty filter

## Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

Use the integer binding `{"_gsp_p0":1}` for both.

```gremlin
// q1
g.inject(1)
    .V()
    .hasLabel('ScorRoot')
    .has('uid', P.eq(_gsp_p0))
    .as('_gsp_v0')
    .outE('GSP_SC_HIGH')
    .inV()
    .hasLabel('ScorTarget')
    .as('_gsp_v1')
    .filter(__.limit(0))
    .project('c0')
    .by(__.constant(1L));

// q2
g.inject(1)
    .V()
    .hasLabel('ScorRoot')
    .has('uid', P.eq(_gsp_p0))
    .as('_gsp_v0')
    .outE('GSP_SC_REF')
    .inV()
    .hasLabel('ScorTarget')
    .as('_gsp_v1')
    .filter(__.limit(0))
    .project('c0')
    .by(__.constant(1L));
```

Both queries return no rows. The child traversal `__.limit(0)` is empty for every input, independently of the graph, and the surrounding traversal only reads data. Changing only the relationship type produces a median paired q1/q2 runtime ratio of **65.46×**.

## Which ArcadeDB versions are affected?

I tested the ArcadeDB **26.10.2** release distribution, build `e854692736b48971f92dff78a1e727bc570bb6a2` (`1792085686249/main`), with TinkerPop **3.8.2** and the default Java Gremlin engine through native HTTP. The server ran in a Linux/arm64 Docker container on macOS ARM64, with `-Xms1g -Xmx4g`.

## How to reproduce

Start with an empty database. Run these statements as SQL.

```sql
CREATE VERTEX TYPE ScorRoot;
CREATE PROPERTY ScorRoot.uid LONG;
CREATE PROPERTY ScorRoot.id LONG;
CREATE PROPERTY ScorRoot.key LONG;
CREATE PROPERTY ScorRoot.expected_count LONG;
CREATE VERTEX TYPE ScorTarget;
CREATE PROPERTY ScorTarget.uid LONG;
CREATE PROPERTY ScorTarget.mark BOOLEAN;
CREATE PROPERTY ScorTarget.key LONG;
CREATE EDGE TYPE GSP_SC_HIGH;
CREATE EDGE TYPE GSP_SC_REF;
```

Run these statements as openCypher.

```cypher
CREATE (:ScorRoot {uid: 1, id: 1, key: 1, expected_count: 200000});

MATCH (r:ScorRoot {uid: 1})
UNWIND range(1, 200000) AS i
CREATE (r)-[:GSP_SC_HIGH]->(:ScorTarget {uid: 895440 + i, mark: true, key: 1});

MATCH (r:ScorRoot {uid: 1})
UNWIND range(2, 4) AS i
CREATE (r)-[:GSP_SC_REF]->(:ScorTarget {uid: i, mark: true, key: 1});
```

Create the index as SQL.

```sql
CREATE INDEX gsp_cost_lookup ON ScorRoot (id) NOTUNIQUE;
```

Run q1 and q2 through the Gremlin query endpoint with `_gsp_p0` bound to `1`. I used `limit: 10001` and `serializer: "record"` for both requests.

There is one `ScorRoot` with `uid=1`, 200,000 outgoing `GSP_SC_HIGH` relationships and three outgoing `GSP_SC_REF` relationships. All destinations are `ScorTarget` vertices. The index on `id` is retained from the measured setup, although these queries select the root by `uid`.

For q1, I get no rows: `[]`. Median runtime: **207.18 ms**.

For q2, I also get no rows: `[]`. Median runtime: **3.20 ms**.

I rebuilt the graph twice and measured 20 balanced AB/BA pairs per rebuild after five warm-up pairs, plus ten A/A and ten B/B control pairs, reading and decoding each full HTTP result without profiling. Across the 40 ordinary paired runs, the median q1/q2 ratio was **65.46×** (95% bootstrap interval **59.05–72.29×**) and the median paired difference was **201.98 ms**; the reported ratio is the median of the paired ratios.

In separate requests, setting `profileExecution` to `detailed` produces these native GremlinExecutionPlan excerpts. `cost` and `totalCost` are PROFILE nanoseconds, with nested steps included in `totalCost`.

```text
q1:
ArcadeFilterByTypeStep(vertex,ScorRoot)
  elements=1, traversers=1, cost=59624, totalCost=59624
VertexStep(OUT,[GSP_SC_HIGH],vertex)
  elements=200000, traversers=200000, cost=82721834, totalCost=82721834
TraversalFilterStep([RangeGlobalStep(0,0)])@[_gsp_v1]
  elements=0, traversers=0, cost=91874641, totalCost=138433448
q2:
ArcadeFilterByTypeStep(vertex,ScorRoot)
  elements=1, traversers=1, cost=18584, totalCost=18584
VertexStep(OUT,[GSP_SC_REF],vertex)
  elements=3, traversers=3, cost=1338624, totalCost=1338624
TraversalFilterStep([RangeGlobalStep(0,0)])@[_gsp_v1]
  elements=0, traversers=0, cost=27081, totalCost=30415
```

The plan retains `TraversalFilterStep([RangeGlobalStep(0,0)])` after the expansion: q1 emits 200,000 neighbors into this filter, while q2 emits three, and both filters emit zero. [`FilterStep`](https://github.com/apache/tinkerpop/blob/3.8.2/gremlin-core/src/main/java/org/apache/tinkerpop/gremlin/process/traversal/step/filter/FilterStep.java#L34-L40) pulls upstream input before testing it, while [`InlineFilterStrategy`](https://github.com/apache/tinkerpop/blob/3.8.2/gremlin-core/src/main/java/org/apache/tinkerpop/gremlin/process/traversal/strategy/optimization/InlineFilterStrategy.java#L187-L201) excludes range steps from pure-filter inlining. This read-only child filter always rejects its input, so the preceding neighbor expansion can be skipped.

## Expected performance

Please recognize this always-empty child filter and skip the preceding read-only neighbor expansion.
