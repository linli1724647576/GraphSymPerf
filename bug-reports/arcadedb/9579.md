# COUNT subquery runs before a false AND condition

## Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

```cypher
// q1
MATCH (u:GspAnchor) WHERE ((coalesce(u.keep, false) = true) AND (COUNT { MATCH (u)-[:GSP_EXPAND]->(gsp_leaf:GspLeaf) WHERE (coalesce(gsp_leaf.mark, false) = true) } > 0)) RETURN u.uid AS c0;

// q2
MATCH (u:GspAnchor) WHERE ((COUNT { MATCH (u)-[:GSP_EXPAND]->(gsp_leaf:GspLeaf) WHERE (coalesce(gsp_leaf.mark, false) = true) } > 0) AND (coalesce(u.keep, false) = true)) RETURN u.uid AS c0;
```

Both queries return `c0 = 2` on the graph below. I swap the operands of `AND` in q2. The first node has `keep=false`, so its neighbors cannot change the result, but q2 performs over 800,000 record lookups before excluding it. I measured about a 192-fold q2/q1 runtime difference.

## Which ArcadeDB versions are affected?

I tested ArcadeDB **26.10.1-SNAPSHOT**, build `ebdf527641ba444364bb9e29aa020e9e04824862` (`1788464335463/main`), a development snapshot. I ran openCypher through the HTTP query interface in Docker on macOS ARM64. The native PROFILE identifies the cost-based optimizer; the property index below is an `LSM_TREE` index.

## How to reproduce

Start with an empty database. Create the schema using SQL:

```sql
CREATE VERTEX TYPE GspAnchor;
CREATE PROPERTY GspAnchor.uid LONG;
CREATE PROPERTY GspAnchor.keep BOOLEAN;
CREATE VERTEX TYPE GspLeaf;
CREATE PROPERTY GspLeaf.uid LONG;
CREATE PROPERTY GspLeaf.mark BOOLEAN;
CREATE EDGE TYPE GSP_EXPAND;
CREATE EDGE TYPE GSP_REFERENCE;
```

Load the following data using openCypher:

```cypher
CREATE (:GspAnchor {uid: 1, keep: false});

CREATE (:GspAnchor {uid: 2, keep: true})-[:GSP_EXPAND]->(:GspLeaf {uid: 3, mark: true});

MATCH (u:GspAnchor {uid: 1}) UNWIND range(1, 400000) AS i CREATE (u)-[:GSP_EXPAND]->(:GspLeaf {uid: 895440 + i, mark: false});

MATCH (u:GspAnchor) WHERE coalesce(u.keep, false) = true MATCH (u)-[:GSP_EXPAND]->(v:GspLeaf) CREATE (u)-[:GSP_REFERENCE]->(v);
```

Create the property index using SQL, then run q1 and q2 above:

```sql
CREATE INDEX gsp_cost_lookup ON GspAnchor (uid) NOTUNIQUE;
```

Node 1 has `keep=false` and 400,000 outgoing `GSP_EXPAND` relationships to nodes with `mark=false`. Node 2 has `keep=true` and one outgoing relationship to node 3, whose `mark=true` makes node 2 the only result. The extra `GSP_REFERENCE` relationship and the `uid` index remain in the measured database.

For q1, I get one row: `c0 = 2`. Median runtime: **1.24 ms**.

For q2, I get the same row. Median runtime: **226.69 ms**.

I rebuilt this graph twice and measured 20 paired runs per rebuild, with five warm-up pairs before each set. I read the full results and included HTTP response transfer and decoding in the runtime; I did not use `PROFILE` for these timings. Across the 40 paired runs, the median q2/q1 ratio was **191.63×** and the median paired time difference was **224.52 ms**.

Adding `PROFILE` gives the following excerpts. `Rows Returned` is the actual result count; `Estimated Rows` is a planning estimate.

```text
q1:
Execution Time: 0.515 ms
Rows Returned: 1
Physical operator: NodeByLabelScan(u:GspAnchor)
Estimated Cost: 2.00
Estimated Rows: 2
FilterPropertiesStep: 164 microseconds, 1 row
ProjectReturnStep: 12 microseconds, 1 row

q2:
Execution Time: 254.992 ms
Rows Returned: 1
Physical operator: NodeByLabelScan(u:GspAnchor)
Estimated Cost: 2.00
Estimated Rows: 2
FilterPropertiesStep: 66 microseconds, 1 row
ProjectReturnStep: 17 microseconds, 1 row
```

The physical plan retains each query's `AND` operand order in the filter attached to `NodeByLabelScan`. For q2, ArcadeDB evaluates the `COUNT` for node 1 before reading `keep=false`; q1 checks `keep` first and skips that count. The outer PROFILE does not expose the nested COUNT's work: its `FilterPropertiesStep` row count is 1 for both queries, while the separate native profiler records 10 versus 800,411 record lookups in each of two runs. I obtained these lookup counts from separate, single-query `profiler start`/`profiler stop` windows. ArcadeDB's `readRecord` counter includes cached record lookups; it does not count edge visits or Neo4j DB Hits.

## Expected performance

Could you evaluate the inexpensive `keep` condition before this `COUNT` in q2, as q1 does, so that you skip the 400,000-neighbor branch for node 1?
