# Read-only CALL UNION ALL materializes branches before LIMIT 3

## Describe the situation

Hi, ArcadeDB developers,

Please consider these two queries:

```cypher
// q1
CALL () {
MATCH (r:GspRoot)-[:GSP_WITNESS]->(w:GspWitness)
WHERE w.keep = true
RETURN 1 AS item
UNION ALL
MATCH (r:GspRoot)-[:GSP_LOW]->(n:GspLow)
WHERE n.keep = true
RETURN 1 AS item
}
RETURN item AS answer
LIMIT 3

// q2
CALL () {
MATCH (r:GspRoot)-[:GSP_WITNESS]->(w:GspWitness)
WHERE w.keep = true
RETURN 1 AS item
UNION ALL
MATCH (r:GspRoot)-[:GSP_HIGH]->(n:GspHigh)
WHERE n.keep = true
RETURN 1 AS item
}
RETURN item AS answer
LIMIT 3
```

Both queries return three integer `1` rows. The witness branch already provides three rows; the second branch contains two matches in q1 and 300,000 matches in q2. All branches project `1`, so those extra matches cannot change the limited result. I measured about a 42.7-fold q2/q1 runtime difference.

## Which ArcadeDB versions are affected?

I tested ArcadeDB 26.10.2, build `e854692736b48971f92dff78a1e727bc570bb6a2`, through native HTTP Cypher in Docker on macOS ARM64. The container had 2 CPUs and 3 GiB of memory; the JVM used `-Xms256m -Xmx1024m`. The plans shown below use the traditional execution path.

## How to reproduce

In an empty database, run these schema statements as SQL:

```sql
CREATE VERTEX TYPE GspRoot;
CREATE PROPERTY GspRoot.uid LONG;
CREATE INDEX ON GspRoot (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspLow;
CREATE PROPERTY GspLow.uid LONG;
CREATE PROPERTY GspLow.keep BOOLEAN;
CREATE INDEX ON GspLow (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspHigh;
CREATE PROPERTY GspHigh.uid LONG;
CREATE PROPERTY GspHigh.keep BOOLEAN;
CREATE INDEX ON GspHigh (uid) NOTUNIQUE;
CREATE VERTEX TYPE GspWitness;
CREATE PROPERTY GspWitness.uid LONG;
CREATE PROPERTY GspWitness.keep BOOLEAN;
CREATE INDEX ON GspWitness (uid) NOTUNIQUE;
CREATE EDGE TYPE GSP_LOW;
CREATE EDGE TYPE GSP_HIGH;
CREATE EDGE TYPE GSP_WITNESS;
```

Then run these Cypher statements to create the graph:

```cypher
CREATE (:GspRoot {uid:0});

UNWIND range(1,2) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_LOW]->(:GspLow {uid:i,keep:true});

UNWIND range(3,5) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_WITNESS]->(:GspWitness {uid:i,keep:true});

UNWIND range(6,300005) AS i
MATCH (r:GspRoot {uid:0})
CREATE (r)-[:GSP_HIGH]->(:GspHigh {uid:i,keep:true});
```

Run q1 and q2 above on this same graph. It has one root, two low leaves, three witness leaves and 300,000 high leaves. All leaves have `keep=true`; each vertex type has the shown `uid` index.

For q1, I get three rows: `answer = 1` in each row. Median runtime: **7.46 ms**.

For q2, I get the same result. Median runtime: **318.71 ms**.

I ran two independently rebuilt sessions. Each used 3 warmup pairs and 6 screening pairs, followed by 5 warmup pairs and 20 alternating AB/BA confirmation pairs; the medians above are from the second confirmation and include complete result consumption. Both sessions exceeded 5x and 100 ms, with the same slower side in every confirmation pair.

The q2/q1 ratio of timing medians is **42.75x**; the median signed paired difference is **297.68 ms**. PROFILE was collected separately after timing.

The [seeded UNION path](https://github.com/ArcadeData/arcadedb/blob/e854692736b48971f92dff78a1e727bc570bb6a2/engine/src/main/java/com/arcadedb/query/opencypher/executor/CypherExecutionPlan.java#L531-L571) consumes every branch into a list before returning. [SubqueryStep](https://github.com/ArcadeData/arcadedb/blob/e854692736b48971f92dff78a1e727bc570bb6a2/engine/src/main/java/com/arcadedb/query/opencypher/executor/steps/SubqueryStep.java#L432-L453) then collects that ResultSet again. The three-row demand therefore cannot stop the high branch after the witness prefix; the [top-level read-only UNION path](https://github.com/ArcadeData/arcadedb/blob/e854692736b48971f92dff78a1e727bc570bb6a2/engine/src/main/java/com/arcadedb/query/opencypher/executor/CypherExecutionPlan.java#L832-L858) already streams.

## Expected performance

Please stream the read-only seeded `UNION ALL` through `CALL` so the first branch can satisfy `LIMIT 3` before the full second branch is evaluated.
