# An edge check between two bound match() vertices reads every edge of the high-degree endpoint

## Describe the situation

Hi, Apache HugeGraph developers,

Please consider these two queries. Bind `p0` to the integer `1` for both.

```groovy
// q1
g.V().hasLabel("Random_label_3").has("p_anchor",p0)
 .match(
   __.as("p_match_u").out("Pattern_p_left_edge").hasLabel("Pattern_p_match_label_0").as("p_match_0"),
   __.as("p_match_u").where(__.out("Pattern_p_right_edge").as("p_match_0")))
 .select("p_match_u").constant(false)

// q2
g.V().hasLabel("Random_label_3").has("p_anchor",p0)
 .match(
   __.as("p_match_u").out("Pattern_p_left_edge").hasLabel("Pattern_p_match_label_0").as("p_match_0"),
   __.as("p_match_0").where(__.in("Pattern_p_right_edge").as("p_match_u")))
 .select("p_match_u").constant(false)
```

Both queries ask whether a `Pattern_p_right_edge` edge connects the two vertices already bound to `p_match_u` and `p_match_0`. q1 checks it from `p_match_u`, q2 from `p_match_0`. They return the same single row. `p_match_0` has about 100,000 incoming `Pattern_p_right_edge` edges, and q2 reads all of them before it finds `p_match_u`. q2 takes about 94 times as long as q1.

## Which Apache HugeGraph versions are affected?

I tested HugeGraph 1.7.0 (TinkerPop 3.5.1) with the RocksDB backend, the `hugegraph/hugegraph:1.7.0` Docker image on macOS ARM64, 2 CPUs and 3 GiB memory, GraphSON 3 over the Gremlin HTTP endpoint, and default strategies.

The setup creates 100,051 vertices and 100,102 edges. Run q1 and q2 above on this graph.

The relevant part of the data:

- One `Random_label_3` vertex `u` has `p_anchor = 1`. It has one `Pattern_p_left_edge` edge and one `Pattern_p_right_edge` edge, both to the same `Pattern_p_match_label_0` vertex `t`.
- `t` has 100,001 incoming `Pattern_p_right_edge` edges: the one from `u` and 100,000 from other `Random_label_3` vertices.
- The 100,000 `Random_label_3` vertices that point at `t` have `p_anchor = 0`; the remaining background `Random_label_3` vertices have no `p_anchor`. Only `u` matches `p_anchor = 1`.

For q1, I get one row: `false`. Median runtime: 1.235 ms.

For q2, I get one row: `false`. Median runtime: 115.870 ms.

Each runtime is the median of 20 runs per query, alternating q1/q2 and q2/q1 order, after 5 warm-up pairs, with the full result read. The median paired q2/q1 ratio is 95.3x. `PROFILE` ran after the timed runs.

PROFILE excerpt for q1 (traverser counts):

```text
MatchStartStep(p_match_u)                                    traversers=1
WhereTraversalStep([WhereStartStep, HugeVertexStep(OUT,[Pattern_p_right_edge],vertex), WhereEndStep(p_match_0)])
  HugeVertexStep(OUT,[Pattern_p_right_edge],vertex)          traversers=1
```

PROFILE excerpt for q2:

```text
MatchStartStep(p_match_0)                                    traversers=1
WhereTraversalStep([WhereStartStep, HugeVertexStep(IN,[Pattern_p_right_edge],vertex), WhereEndStep(p_match_u)])
  HugeVertexStep(IN,[Pattern_p_right_edge],vertex)           traversers=100001
```

In q2, `HugeVertexStep(IN,...)` loads every incoming edge of `t` and every adjacent vertex, and `WhereEndStep(p_match_u)` compares each one with `u`. In q1 the same check starts at `u`, which has a single `Pattern_p_right_edge` edge. Both endpoints are already known when the `where()` runs, so the edge could be found from either side without listing the high-degree side.

## Expected performance

When the end of `where(in(label).as(x))` or `where(out(label).as(x))` is compared with an already bound vertex, I would like HugeGraph to look up the edge to that vertex directly, instead of listing the whole adjacency of the start vertex, as q1 effectively does when it starts from the low-degree endpoint.
