# Gremlin not(out().has()) is slower on an edge label with more matching neighbors

## Describe the situation

Hi, Apache HugeGraph developers,

Please consider these two queries. Bind `p0` to `true` for both.

```groovy
// q1
g.V().hasLabel("Random_label_1")
 .filter(__.not(__.out("Pattern_p_low_edge").has("keep",p0)))
 .identity()

// q2
g.V().hasLabel("Random_label_1")
 .filter(__.not(__.out("Pattern_p_high_edge").has("keep",p0)))
 .identity()
```

Each `Random_label_1` vertex has a neighbor with `keep = true` on both edge labels, so both `not(...)` filters reject every vertex and both queries return no rows. For each vertex, the first adjacent vertex already decides the result. q2 follows an edge label with 2,000 neighbors per vertex instead of one, and takes about 20 times as long as q1.

## Which Apache HugeGraph versions are affected?

I tested HugeGraph 1.7.0 (TinkerPop 3.5.1) with the RocksDB backend, the `hugegraph/hugegraph:1.7.0` Docker image on macOS ARM64, 2 CPUs and 3 GiB memory, GraphSON 3 over the Gremlin HTTP endpoint, and default strategies.

The setup creates 100,100 vertices and 100,150 edges. Run q1 and q2 above on this graph.

The relevant part of the data:

- There are 50 `Random_label_1` vertices.
- Each has one `Pattern_p_low_edge` edge and 2,000 `Pattern_p_high_edge` edges.
- Every target vertex of both edge labels has `keep = true`.

For q1, I get no rows. Median runtime: 1.693 ms.

For q2, I get no rows. Median runtime: 33.465 ms.

Each runtime is the median of 6 runs per query, alternating q1/q2 and q2/q1 order, after 3 warm-up pairs, with the full result read. The median paired q2/q1 ratio is 20.0x. With 200 instead of 2,000 high-edge neighbors per vertex, the same queries take 1.19 ms and 10.87 ms. `PROFILE` ran after the timed runs.

PROFILE excerpt for q1 and q2 (the step lists after strategies):

```text
q1: NotStep([HugeVertexStep(OUT,[Pattern_p_low_edge],Vertex,[keep.eq(true)])])
q2: NotStep([HugeVertexStep(OUT,[Pattern_p_high_edge],Vertex,[keep.eq(true)])])
```

The `has("keep",true)` test is folded into `HugeVertexStep`, so the step itself decides which adjacent vertices qualify. `NotStep` needs only to know whether one qualifies. q2 still grows with the number of neighbors: about 0.6 ms more per start vertex with 2,000 neighbors, and about 0.2 ms with 200. That suggests `HugeVertexStep` reads and checks a whole batch of adjacent vertices before it returns the first one.

## Expected performance

When `HugeVertexStep` with a folded vertex condition is used inside `not()`, `filter()` or `where()`, I would like it to return the first qualifying adjacent vertex as soon as it is found, so that the existence check costs about the same for one neighbor as for 2,000, as q1 does.
