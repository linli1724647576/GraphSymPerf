# Reversing endpoint order in a single undirected path drops the index scan

## Describe the situation

Hi, FalkorDB developers,

Please consider these two queries:

```cypher
// q1
MATCH p=(r:GspRoot {uid:1})-[:GSP_PATH*1..2]-(t:GspLeaf)
WHERE all(n IN nodes(p) WHERE n.keep=true)
RETURN r.uid AS root_uid, t.uid AS leaf_uid, length(p) AS hops;

// q2
MATCH p=(t:GspLeaf)-[:GSP_PATH*1..2]-(r:GspRoot {uid:1})
WHERE all(n IN nodes(p) WHERE n.keep=true)
RETURN r.uid AS root_uid, t.uid AS leaf_uid, length(p) AS hops;
```

I write the same undirected path from the other endpoint in q2, keeping its bounds, condition and projected endpoint identities. Both queries return one row, but q1 starts from the indexed root and q2 scans every leaf before traversing the graph. I measured q2 taking about 701.0 times as long as q1.

## Which FalkorDB versions are affected?

I tested FalkorDB 6.0.3 (module version 60003, Rust engine) in Docker on macOS ARM64, using FalkorDB Python driver 1.8.1 and redis-py 8.1.0. Each fresh container had 2 CPUs and 2 GiB of memory. The result cap was disabled with `GRAPH.CONFIG SET RESULTSET_SIZE -1`; queries used a native 10-second timeout.

## How to reproduce

Run these statements in an empty graph, wait for the root index to become `OPERATIONAL`, then execute q1 and q2 above:

```cypher
CREATE INDEX FOR (n:GspRoot) ON (n.uid);

CREATE (r:GspRoot {uid:1,keep:true}),
       (b:GspBlocked {uid:2,keep:false}),
       (t:GspLeaf {uid:3,keep:true})
CREATE (r)-[:GSP_PATH]->(b),
       (r)-[:GSP_PATH]->(t);

MATCH (b:GspBlocked {uid:2})
UNWIND range(1,10000) AS i
CREATE (b)-[:GSP_PATH]->(:GspLeaf {uid:100+i,keep:true});
```

The graph contains one indexed root, one blocked middle node and 10,001 leaves. One leaf is connected directly to the root and provides the valid one-hop path. The other 10,000 leaves are behind the middle node with `keep=false`, so those two-hop paths cannot satisfy the condition.

For q1, I get one row in columns `(root_uid, leaf_uid, hops)`: `(1, 3, 1)`. Median runtime: **6.45 ms**.

For q2, I get the same row. Median runtime: **4521.40 ms**.

These figures are from 20 alternating AB/BA confirmation pairs after five warm-up pairs in the second of two independently created containers and graph loads. Each session first ran three warm-up pairs and six screening pairs. I read the full results for every execution; ordinary timings include client round trips and result decoding, and exclude setup and profiling. The q2/q1 ratio of confirmation medians is **700.98x**; the median signed paired difference is **4515.30 ms**.

The separately collected native profiles show:

```text
q1 (GRAPH.PROFILE excerpt):
Project | Records produced: 1, Execution time: 0.026375 ms
    Filter | Records produced: 1, Execution time: 4.343666 ms
        Conditional Variable Length Traverse | (r)-[_anon_0:GSP_PATH*1..2]->(t) | Records produced: 10001, Execution time: 2.247042 ms
            Node By Index Scan | (r:GspRoot) | Records produced: 1, Execution time: 0.006042 ms

q2 (GRAPH.PROFILE excerpt):
Project | Records produced: 1, Execution time: 0.024834 ms
    Filter | Records produced: 1, Execution time: 4.027875 ms
        Conditional Variable Length Traverse | (t)-[_anon_0:GSP_PATH*1..2]->(r) | Records produced: 10001, Execution time: 4513.836836 ms
            Node By Label Scan | (t:GspLeaf) | Records produced: 10001, Execution time: 0.225124 ms
```

Q1 seeds the traversal from one indexed root; q2 seeds it from a label scan of 10,001 leaves. Both traversal operators output 10,001 records before the path filter, so these output counts do not measure internal DFS visits. The endpoint-selection pass [skips bidirectional relationships](https://github.com/FalkorDB/FalkorDB/blob/c937aa4fafa9a0e9ab4afb007885be4fa30f1629/graph/src/planner/optimizer/select_scan_node.rs#L540-L549), which is consistent with the observed orientation dependence.

This case has one path pattern, whereas [#2558](https://github.com/FalkorDB/FalkorDB/issues/2558) is triggered by adding a second pattern. It also differs from the path-predicate pruning request [#3315](https://github.com/FalkorDB/FalkorDB/issues/3315): removing `ALL` still leaves the index-scan versus label-scan gap, with both reflected queries returning the same 10,001 rows. Those control queries took about 40–62 ms versus 4.56–4.57 seconds in three ordinary runs on a separate fresh graph.

## Expected performance

Could FalkorDB choose the selective indexed endpoint for this single undirected variable-length pattern regardless of which endpoint is written first, as q1 already does, while preserving the path's observable orientation?
